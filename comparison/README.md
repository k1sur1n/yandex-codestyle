# Сравнение подходов: Яндекс и Google

> Данные актуальны на 2026-10-09.

Обе компании держат почти весь код в монорепозитории с собственной системой контроля версий и сборкой, работают по модели trunk-based, обязательно ревьюят каждое изменение и отдают формат инструменту, а не ревьюеру. Поэтому совпадений между ними больше, чем различий.

Различия начинаются там, где правило записано. Google публикует один репозиторий гайдов-«законов» с владельцами по языкам, гайд по ревью, процедуру выпуска открытого проекта и принципы ML-инженерии. У Яндекса публичные правила живут в файлах открываемых проектов, в дефолтных конфигах инструмента сборки и в пакетах Gravity UI; всё остальное для git-репозитория приходится реконструировать по 25 открытым репозиториям.

В коде это даёт два далёких друг от друга C++ (исключения, префиксы `T`/`I`/`E`/`N` и строка без предела против `absl::Status`, имён без префиксов и 80 колонок), два близких Python, которые расходятся в импортах и docstring, и несимметричный фронтенд: Angular у Google против React с БЭМ и Gravity UI у Яндекса. Этот файл входит в сравнение первым: здесь главные отличия, сводная таблица и навигация по семи остальным документам раздела.

## Главные отличия

В каждом пункте ID правил двух профилей: `Y-…` из [профиля Яндекса](../README.md), `G-…` из [профиля Google](https://github.com/k1sur1n/google-codestyle/blob/main/README.md). Ссылка на ID ведёт в документ, где правило описано с проверкой и источником. Факты в документах со ссылками на источники; выводы о причинах помечены там словом «Интерпретация».

1. **Где живут правила.** У Google один репозиторий google/styleguide с 17 гайдами по языкам, копиями внутренних документов, в который внешние правки не принимаются; плюс eng-practices, документация Open Source Programs Office и книга «Software Engineering at Google». У Яндекса центрального сайта нет: C++-гайд лежит в репозитории CatBoost, Python-гайд у команды YTsaurus, дефолтные конфиги линтеров в `yandex/yatool`, веб-конфиги в npm-пакетах Gravity UI, правила репозитория в CONTRIBUTING отдельных проектов. Поэтому правила Google это пересказ письменного текста, а правила Яндекса о git и ML по большей части реконструкция с выборкой и долей. Подробнее: [approach.md, раздел 3](approach.md#3-как-правила-создаются-и-поддерживаются).

2. **Что регулирует текст.** Гайды Google это перечни языковых вердиктов: в C++ запрещены исключения, модули, `long double`, `using namespace`, статические объекты с нетривиальным деструктором ([G-CPP-034](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/cpp.md), [G-CPP-040](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/cpp.md) … [G-CPP-045](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/cpp.md)), в Python `staticmethod`, несколько `for` в comprehension, метаклассы ([G-PY-049](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/python.md) … [G-PY-060](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/python.md)). Единственный общий гайд Яндекса, наоборот, объявляет, что описывает «только то, что отрицательно влияет на читаемость», а дефолтные конфиги Аркадии мягкие: `ColumnLimit: 0`, пять групп ruff ([Y-CPP-018](../docs/languages/cpp.md), [Y-PY-036](../docs/languages/python.md)). Строгость у Яндекса сосредоточена в именах ([Y-CPP-020](../docs/languages/cpp.md) … [Y-CPP-023](../docs/languages/cpp.md)) и в правиле «один файл, один стиль» ради авторства строк ([Y-CPP-068](../docs/languages/cpp.md)). Подробнее: [approach.md, раздел 1](approach.md#1-философия-что-оптимизируют-правила).

3. **Как правила принуждаются.** У Google цепочка описана в книге: форматтер в presubmit, компилятор без предупреждений, Tricorder в ревью, LSC для старого кода и readability, персональная сертификация по языку, которая действует только в монорепозитории. У Яндекса публично видны `ya style`, стиль как тип теста в `ya test`, правила ревью в `a.yaml` и с 2026 года ИИ-ревью первым проходом; аналога readability не найдено. В профилях это превращается в «что умеет инструмент, проверяет инструмент» ([G-CR-005](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/code-review.md)) и «автоматика раньше людей» ([Y-CR-006](../docs/git/code-review.md), [Y-CR-012](../docs/git/code-review.md)). Подробнее: [approach.md, раздел 4](approach.md#4-как-обеспечивается-соблюдение).

4. **Ошибки в C++: исключения против `absl::Status`.** Это самое дорогое различие, потому что оно меняет сигнатуры, а не оформление. Аркадийный гайд требует сообщать об ошибках исключениями ([Y-CPP-048](../docs/languages/cpp.md)); гайд Google запрещает их полностью и объясняет запрет историей своей кодовой базы ([G-CPP-034](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/cpp.md), [G-CPP-035](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/cpp.md)). Код, написанный по одному профилю, не переводится в другой автозаменой. Подробнее: [code.md, «Ошибки»](code.md#ошибки-исключения-против-abslstatus) и пара «класс на C++» в [examples.md](examples.md#1-класс-на-c).

5. **Имена и раскладка C++.** У Яндекса префиксы `TFoo`, `IFoo`, `EFoo`, `NFoo`, поля `Name_`, переменные `camelCase`, 4 пробела, `#pragma once`, стандартная библиотека последней в списке include ([Y-CPP-001](../docs/languages/cpp.md), [Y-CPP-020](../docs/languages/cpp.md) … [Y-CPP-027](../docs/languages/cpp.md), [Y-CPP-035](../docs/languages/cpp.md), [Y-CPP-039](../docs/languages/cpp.md)). У Google `Foo`, `snake_case`, `kConstant`, 2 пробела и 80 колонок, `#define`-guard от пути файла и стандартная библиотека сразу после парного заголовка ([G-CPP-001](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/cpp.md), [G-CPP-002](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/cpp.md), [G-CPP-011](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/cpp.md) … [G-CPP-013](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/cpp.md), [G-CPP-019](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/cpp.md), [G-CPP-022](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/cpp.md)). Совпадают они в C++20, PascalCase функций, `override`, `nullptr` и обязательных фигурных скобках. Подробнее: [code.md, таблица C++](code.md#c-таблица).

6. **Python: что надстроено над PEP 8.** Обе компании стоят на PEP 8. Google добавляет правила, которых в нём нет и которые ни один публичный инструмент не проверяет: импортировать только модули, без относительных импортов, сортировка по полному пути ([G-PY-017](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/python.md), [G-PY-018](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/python.md), [G-PY-022](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/python.md)), docstring с секциями `Args:`/`Returns:`/`Raises:` ([G-PY-027](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/python.md), [G-PY-028](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/python.md)), 80 колонок и обязательный `pylintrc` ([G-PY-002](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/python.md), [G-PY-048](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/python.md)). Профиль Яндекса почти целиком выражается конфигом: `ruff format` на 120 символах, двойные кавычки, isort по PEP 8, mypy с обязательными аннотациями ([Y-PY-001](../docs/languages/python.md), [Y-PY-002](../docs/languages/python.md), [Y-PY-011](../docs/languages/python.md), [Y-PY-031](../docs/languages/python.md)). Подробнее: [code.md, «Импорты»](code.md#импорты-главное-отличие-python).

7. **Фронтенд: гайд против конфигов.** Google публикует TypeScript-гайд и Angular Style Guide редакции 2025 года ([G-TS-004](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/other.md), [G-NG-004](https://github.com/k1sur1n/google-codestyle/blob/main/docs/frameworks/angular.md), [G-NG-022](https://github.com/k1sur1n/google-codestyle/blob/main/docs/frameworks/angular.md)) и ни строчки о React. Яндекс не публикует прозаических гайдов, но поддерживает живые конфиги Gravity UI и методологию БЭМ ([Y-TS-001](../docs/languages/other.md), [Y-REACT-014](../docs/frameworks/react.md), [Y-CSS-001](../docs/frameworks/react.md) … [Y-CSS-003](../docs/frameworks/react.md)), а об Angular у него публичных данных не найдено. БЭМ-имена с `__` и `_` прямо противоречат правилу Google «слова в имени класса разделяются только дефисом» ([G-CSS-012](https://github.com/k1sur1n/google-codestyle/blob/main/docs/frameworks/angular.md)). Подробнее: [code.md, «Фронтенд»](code.md#фронтенд).

8. **Права на уровне файла или на уровне репозитория.** Google требует заголовок лицензии в каждом файле с кодом и CLA с проверкой ботом ([G-REPO-010](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/repository.md) … [G-REPO-013](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/repository.md), [G-REPO-017](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/repository.md), [G-REPO-023](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/repository.md)); в выборке заголовки стоят в 19 из 24 репозиториев. У Яндекса заголовков нет ни в одном из 25: лицензия фиксируется один раз в `LICENSE`, CLA без автоматики, а флагманы YDB, YTsaurus и CatBoost от него отказались ([Y-REPO-004](../docs/git/repository.md), [Y-REPO-007](../docs/git/repository.md), [Y-REPO-008](../docs/git/repository.md)). DCO не использует ни одна компания. Подробнее: [repository.md, раздел 2](repository.md#2-лицензии-cla-и-dco-заголовки-в-файлах-сторонний-код-дисклеймеры).

9. **Сообщения коммитов.** На похожих данных профили приняли противоположные решения. Профиль Яндекса берёт Conventional Commits со строчной буквы и ключом задачи в конце заголовка ([Y-GIT-002](../docs/git/commits.md), [Y-GIT-005](../docs/git/commits.md), [Y-GIT-008](../docs/git/commits.md)): это единственный формат, который в репозиториях Яндекса записан, проверяется и питает release-please. Профиль Google берёт предложение-приказ с заглавной буквы и `Fixes #N` в футере ([G-GIT-001](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/commits.md), [G-GIT-005](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/commits.md), [G-GIT-009](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/commits.md)) по eng-practices и статье cbea.ms, а Conventional Commits оставляет репозиториям с release-please ([G-GIT-013](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/commits.md)). Подробнее: [repository.md, раздел 3](repository.md#3-сообщения-коммитов) и пара «коммит и PR» в [examples.md](examples.md#4-сообщение-коммита-и-описание-pr).

10. **Ревью: как против кто и когда.** От Google наружу вышел текст о поведении ревьюера: стандарт одобрения, скорость, пометки «Nit:», порядок разрешения споров ([G-CR-002](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/code-review.md) … [G-CR-014](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/code-review.md)). От Яндекса вышла конфигурация ревью: одно одобрение участника команды, владельцы по путям, сроки ответа, устаревание PR через три месяца, откат без ревью ([Y-CR-001](../docs/git/code-review.md), [Y-CR-002](../docs/git/code-review.md), [Y-CR-007](../docs/git/code-review.md), [Y-CR-008](../docs/git/code-review.md), [Y-CR-010](../docs/git/code-review.md)). Это следствие источников, а не культур: о поведении ревьюеров Яндекса публичных данных нет, о конфигурации ревью Google известно только по книге. Подробнее: [repository.md, раздел 5](repository.md#5-код-ревью).

11. **ML: принципы против продуктов.** Google публикует ML-инженерию как принципы (Rules of ML, «Hidden Technical Debt», рубрика ML Test Score, уровни зрелости MLOps) и как собственные фреймворки с гайдами антипаттернов ([G-MLOPS-012](https://github.com/k1sur1n/google-codestyle/blob/main/docs/ml/mlops.md) … [G-MLOPS-019](https://github.com/k1sur1n/google-codestyle/blob/main/docs/ml/mlops.md), [G-LIB-016](https://github.com/k1sur1n/google-codestyle/blob/main/docs/ml/libraries.md)). Яндекс публикует продукты (CatBoost, DataSphere, YTsaurus) и ни одного текста об оформлении ML-кода, а глубокое обучение в его открытом коде идёт на PyTorch; критерий готовности к продакшену профиль Яндекса берёт у Google с пометкой «не Яндекс» ([Y-MLOPS-012](../docs/ml/mlops.md)). Заметная разница практик: у Google запись об эксперименте живёт в трекере, а конфиг это код с `get_config()` ([G-ML-009](https://github.com/k1sur1n/google-codestyle/blob/main/docs/ml/project-structure.md), [G-REPRO-017](https://github.com/k1sur1n/google-codestyle/blob/main/docs/ml/reproducibility.md)); у исследовательской группы Яндекса конфиг это TOML-файл, а `report.json` коммитится в git рядом с ним ([Y-ML-009](../docs/ml/project-structure.md), [Y-REPRO-011](../docs/ml/reproducibility.md)). Подробнее: [ml.md](ml.md).

12. **Документация.** Это единственная тема, где письменных правил у Яндекса не меньше, чем у Google, просто они принадлежат одному проекту: YDB опубликовал гайд по стилю, структуру и порядок ревью документации поверх платформы Diplodoc с двуязычными каталогами `en/` и `ru/` и линтером в CI ([Y-DOC-004](../docs/git/repository.md), [Y-DOC-007](../docs/git/repository.md), [Y-DOC-008](../docs/git/repository.md), [Y-DOC-010](../docs/git/repository.md)). У Google docguide и гайд по языку документации, рассчитанные на английский текст и 80 колонок ([G-DOC-002](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/repository.md), [G-DOC-006](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/repository.md), [G-DOC-011](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/repository.md)). Подробнее: [repository.md, раздел 8](repository.md#8-документация).

## Что общего

Подробно в [approach.md, раздел 10](approach.md#10-что-общего); объяснения причин там помечены как интерпретация.

- Монорепозиторий с собственными VCS и сборкой у обеих, с одинаковым обоснованием: готовые решения не выдержали масштаба.
- Trunk-based development: ветки для релизов, исправления через cherry-pick ([G-BR-001](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/branches.md), [Y-BR-002](../docs/git/branches.md)); в trunk только через ревью, владение по каталогам ([G-CR-016](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/code-review.md), [Y-CR-002](../docs/git/code-review.md)).
- Формат задаёт инструмент, а не текст: оба профиля начинаются с правила «код форматирует форматтер, раскладку на ревью не обсуждают» ([G-PY-001](https://github.com/k1sur1n/google-codestyle/blob/main/docs/languages/python.md), [Y-PY-001](../docs/languages/python.md)).
- Стиль и тесты входят в сборку на каждое изменение; тесты классифицируются по размеру, а не по типу; сторонний код живёт в отдельном каталоге с лицензией ([G-REPO-014](https://github.com/k1sur1n/google-codestyle/blob/main/docs/git/repository.md), [Y-REPO-010](../docs/git/repository.md)).
- Правила принадлежат языкам, а не компании: арбитры по языкам у Google, `cppcommittee` и Python Committee у Яндекса; поверх общего слоя производные стили проектов (Chromium, AOSP; `util`, YTsaurus, userver).
- Публичные инструменты отстают от правил у обеих: cpplint, pytype и eslint-config-google в архиве; CatBoost удалил раздел о `ya style`, YTsaurus не публикует конфиг форматтера.
- Около 40 % правил в обоих профилях проверяет только ревью, и состав этой доли одинаков: содержание комментариев, выбор конструкций языка, дисциплина тестов.

## Как читать

**Факты и интерпретация.** Факт это то, что написано в источнике или измерено по репозиториям; у него есть ссылка и дата. Всё, что объясняет, почему компания так делает, помечено словом «Интерпретация» и привязано к источникам, на которых вывод построен: сами компании таких объяснений не публиковали. Там, где источник искали и не нашли, стоит ровно «публичных данных не найдено».

**Реконструкция.** Правило с пометкой `· реконструкция` это не цитата гайда, а синтез авторов профилей по практике большинства открытых репозиториев; у него указаны выборка и доля, например «6 из 25 репозиториев», а уровень обычно `SHOULD`. У Яндекса это почти всё о git и ML, у Google ветки, релизы, раскладка ML-проекта и `CODEOWNERS`. Пометка `· не Яндекс` или `· не Google` означает, что публичных данных компании нет и взята общепринятая альтернатива: гайд Angular у Яндекса, Rules of React у Google, документация Django и FastAPI у обоих.

**ID правил.** `Y` или `G` (компания), код области (`CPP`, `PY`, `TS`, `REACT`, `GIT`, `CR`, `ML` и другие; полный список в README каждого профиля), трёхзначный номер в порядке появления в документе: `Y-CPP-021`, `G-PY-017`. ID постоянны и не переиспользуются, поэтому на них можно ссылаться в ревью. Профиль Яндекса: [README.md](../README.md), профиль Google: [google-codestyle/README.md](https://github.com/k1sur1n/google-codestyle/blob/main/README.md).

**Два репозитория.** Сравнение опубликовано в обоих репозиториях, [k1sur1n/yandex-codestyle](https://github.com/k1sur1n/yandex-codestyle/tree/main) и [k1sur1n/google-codestyle](https://github.com/k1sur1n/google-codestyle/tree/main), одним и тем же текстом; различаются только ссылки. Ссылки на правила `Y-…` ведут в yandex-codestyle, на правила `G-…` в google-codestyle, поэтому из любого репозитория половина ссылок на правила уходит в парный репозиторий (ветка `main`).

**Выборки.** «19 из 24» и «6 из 25» относятся к репозиториям, измеренным 2026-10-09 (24 у Google, 25 у Яндекса, по 300 последних коммитов), а не к компаниям в целом. Метод и ограничения описаны в разделе «Метод и ограничения» отчётов [research/yandex.md](../research/yandex.md#метод-и-ограничения) и [google-codestyle/research/google.md](https://github.com/k1sur1n/google-codestyle/blob/main/research/google.md#метод-и-ограничения).

## О качестве доказательств

Две стороны сравнения опираются на доказательства разного рода, и это важнее любого отдельного числа. Для Google почти каждое правило это пересказ письменного текста: гайды google/styleguide, eng-practices, документация OSPO, Rules of ML, документация TensorFlow, Keras, JAX и Flax; практика репозиториев нужна там, где текст молчит (ветки, релизы, раскладка ML-проекта). Для Яндекса письменные источники это гайд CatBoost по C++, гайд YTsaurus по Python, дефолтные конфиги `yandex/yatool`, пакеты Gravity UI, документация YDB, DataSphere и CatBoost; всё о git-процессе и большая часть ML реконструированы по открытым репозиториям, а внутренние документы (общий гайд Аркадии, регламент комитетов, требования к коммитам) недоступны.

В числах по индексу правил (подсчёт скриптом, 2026-10-09):

| | Яндекс | Google |
|---|---|---|
| Правил в профиле | 437 | 508 |
| С пометкой «реконструкция» | 120 (27 %) | 45 (9 %) |
| С источником «не Яндекс» / «не Google» | 92 (21 %) | 83 (16 %) |
| Проверяет инструмент целиком / частично / только ревью | 183 / 74 / 180 | 168 / 163 / 177 |
| Уровень MUST | 156 (36 %) | 188 (37 %) |

Реконструкция у Яндекса сосредоточена в git (репозиторий 12 из 17 правил, ревью 6 из 15, релизы 6 из 13) и в ML (структура проекта 15 из 18, воспроизводимость 15 из 16, MLOps 12 из 23); у Google в ветках (4 из 13), релизах (4 из 12), структуре ML-проекта (8 из 17) и воспроизводимости (7 из 19). Полные таблицы по областям лежат в README профилей и в `docs/enforcement.md` каждого профиля ([Яндекс](../docs/enforcement.md), [Google](https://github.com/k1sur1n/google-codestyle/blob/main/docs/enforcement.md)); что искали и не нашли, перечислено в разделах «Чего в публичном доступе нет» отчётов [research/yandex.md](../research/yandex.md#чего-в-публичном-доступе-нет) и [google-codestyle/research/google.md](https://github.com/k1sur1n/google-codestyle/blob/main/research/google.md#чего-в-публичном-доступе-нет). Доли автоматизации это свойство отбора правил в двух профилях, а не измерение того, сколько правил проверяют автоматически сами компании ([approach.md, раздел 4.3](approach.md#43-доля-автоматизированных-правил-в-двух-профилях)).
