# Ноутбуки в репозитории: профиль Яндекса

> Данные актуальны на 2026-10-09.

Письменного правила Яндекса о ноутбуках в git нет: публичных данных не найдено. Документация Yandex DataSphere объясняет, как очистить вывод ячеек и как работать с Git из JupyterLab, но не связывает одно с другим. Практика открытых репозиториев обратна общепринятому совету: ноутбуки там - демонстрации, и коммитятся они с выводами (8 из 9 собственных ноутбуков в выборке `yandex-research`, 4 из 4 в Yandex AI Studio SDK); `nbstripout` и `jupytext` не настроены ни в одном. Профиль поэтому делит ноутбуки на два режима: демонстрационные хранятся с выводами, как у Яндекса, рабочие - без выводов, через `nbstripout` (не Яндекс). Логика в обоих случаях живёт в модулях, а не в ячейках.

Области идентификаторов: `Y-NB` - этот документ, `Y-ML` - [project-structure.md](project-structure.md), `Y-REPRO` - [reproducibility.md](reproducibility.md). Что ещё нельзя коммитить (данные, веса, секреты) - в [mlops.md](mlops.md), правила Y-MLOPS-001 и Y-MLOPS-005.

## 2. Что берёт профиль

Источники расходятся. Общепринятый совет (не Яндекс) - коммитить ноутбуки без выводов: диффы читаются, размер репозитория не растёт, данные и секреты не утекают через вывод ячейки. Практика Яндекса - коммитить демонстрационные ноутбуки с выводами: вывод и есть то, что читатель должен увидеть на GitHub без запуска.

Профиль берёт оба варианта и разводит их по каталогам:

| Режим | Каталог | Выводы в git | Основание |
|---|---|---|---|
| Демонстрационный: пример использования, учебный материал, отчёт с графиками | `examples/`, `tutorials/` или корень репозитория | сохраняются | практика Яндекса (Y-NB-007) |
| Рабочий: исследование, отладка, черновик анализа | `notebooks/` | вычищаются хуком | общепринятая практика, не Яндекс (Y-NB-006) |

Интерпретация: деление на два режима - решение авторов профиля. Оно согласует наблюдаемую практику с задачей командной работы, где ноутбуки правят несколько человек и проходят ревью.

## 3. Ноутбук и модули

### Y-NB-001 · SHOULD · Логику держать в модулях проекта и импортировать её в ноутбук; в ячейках оставлять вызовы, графики и текст
- Проверка: ручное ревью.
- Источник: [tabular-dl-optimizers README, раздел Repository layout](https://github.com/yandex-research/tabular-dl-optimizers/blob/HEAD/README.md) (2026-04-17); [tabm example.ipynb](https://github.com/yandex-research/tabm/blob/main/example.ipynb) (2025-11-10) · практика, выведенная из репозиториев (4 из 4 репозиториев с собственными ноутбуками) · средняя · реконструкция.

В tabular-dl-optimizers каталог `lib/` прямо описан как общие утилиты и помощники для ноутбука, а сам ноутбук строит таблицы и графики статьи из файлов `report.json`.

### Y-NB-002 · SHOULD · Переносить код из ноутбука в модуль, как только он понадобился второй раз - другому ноутбуку, скрипту или тесту
- Проверка: ручное ревью.
- Источник: [Cookiecutter Data Science, Opinions](https://cookiecutter-data-science.drivendata.org/opinions/) (v2.3.0, 2025-07-23) · сторонний источник · высокая · не Яндекс.

У Яндекса момент переноса письменно не определён: публичных данных не найдено. Формулировка Cookiecutter Data Science: ноутбуки - для исследования и объяснения, исходные файлы - для повторения; одну и ту же задачу не решают кодом в нескольких ноутбуках.

### Y-NB-003 · SHOULD · Запуск, который нужно повторять, ставить на расписание или оставлять без присмотра, выполнять скриптом или заданием, а не ноутбуком
- Проверка: ручное ревью.
- Источник: [DataSphere: задания](https://yandex.cloud/ru/docs/datasphere/concepts/jobs/) (2026-06-24) · официальный гайд · средняя · реконструкция.

Документация описывает свойство продукта (задания запускаются вне JupyterLab и не зависят от ноутбуков), а не правило для репозитория. Оформление такого запуска - Y-ML-006 и Y-ML-007.

### Y-NB-004 · SHOULD · Ноутбук должен выполняться сверху вниз на чистом ядре; всё, что нужно после сессии, явно сохранять в файл
- Проверка: ручное ревью.
- Источник: [DataSphere: проект](https://yandex.cloud/ru/docs/datasphere/concepts/project) (2026-06-15) · официальный гайд · средняя; [tabular-dl-optimizers README, раздел Reproducing Paper Artifacts](https://github.com/yandex-research/tabular-dl-optimizers/blob/HEAD/README.md) (2026-04-17) · практика, выведенная из репозиториев (1 из 12) · низкая · реконструкция.

DataSphere предупреждает, что состояние интерпретатора и результаты автоматически не сохраняются; README tabular-dl-optimizers обещает, что ноутбук выполняется сверху вниз и воспроизводит все таблицы и рисунки. Правило объединяет оба наблюдения.

## 4. Выводы ячеек

### Y-NB-005 · SHOULD · Для каждого каталога с ноутбуками выбрать режим - рабочий (без выводов) или демонстрационный (с выводами) - и закрепить выбор в конфиге хуков и в README
- Проверка: частично: опция `files` или `exclude` у хука `nbstripout` в `.pre-commit-config.yaml`; запись в README - ручное ревью.
- Источник: [AsyncReasoning: demo_simple.ipynb](https://github.com/yandex-research/AsyncReasoning/blob/HEAD/demo_simple.ipynb) и другие ноутбуки выборки (клоны от 2026-10-09) · практика, выведенная из репозиториев (с выводами - 8 из 9 собственных ноутбуков) · средняя · реконструкция; [nbstripout README](https://github.com/kynan/nbstripout/blob/main/README.md) (0.9.1, 2026-02-21) · конфиг или инструмент · высокая · не Яндекс.

### Y-NB-006 · SHOULD · Рабочие ноутбуки коммитить без выводов и счётчиков выполнения
- Проверка: хук `nbstripout` (pre-commit) или git-фильтр `nbstripout`; в CI - `nbstripout --verify notebooks/*.ipynb`.
- Источник: [nbstripout README](https://github.com/kynan/nbstripout/blob/main/README.md) (0.9.1, 2026-02-21) · конфиг или инструмент · высокая · не Яндекс.
- Пример:

```yaml
# .pre-commit-config.yaml (фрагмент). nbstripout 0.9.1 - не Яндекс.
# Не запускалось: реестр пакетов недоступен из среды сборки.
# Идентификатор хука и опции сверены с файлами репозитория на теге 0.9.1.
repos:
  - repo: https://github.com/kynan/nbstripout
    rev: 0.9.1
    hooks:
      - id: nbstripout
        files: ^notebooks/
```

В репозиториях Яндекса этого хука нет (0 из 12); правило закрывает пробел общепринятой практикой. У `nbstripout` два способа подключения, и они ведут себя по-разному:

- pre-commit-хук вычищает выводы и в рабочей копии - после коммита их нет и на диске;
- git-фильтр (`nbstripout --install --attributes .gitattributes`) меняет только то, что видит git, рабочая копия остаётся с выводами. Строки `*.ipynb filter=nbstripout` и `*.ipynb diff=ipynb` попадают в `.gitattributes` и коммитятся, но сам фильтр записывается в `.git/config`, поэтому команду установки выполняет каждый разработчик в своём клоне.

Профиль берёт хук: он работает одинаково у всех, кто поставил pre-commit, и не зависит от локальной настройки git. Полезные опции: `--keep-count` сохраняет счётчики выполнения, `--max-size 1k` вычищает только крупные выводы, `--extra-keys` удаляет лишние метаданные.

### Y-NB-007 · SHOULD · Демонстрационные ноутбуки с выводами держать в отдельном каталоге, исключённом из очистки, и ограничивать размер файла
- Проверка: частично: хук `check-added-large-files` из `pre-commit/pre-commit-hooks` с `--maxkb` (общее правило о размере файлов - Y-MLOPS-002 в [mlops.md](mlops.md)); содержимое выводов - ручное ревью.
- Источник: [AI Studio SDK .pre-commit-config.yaml](https://github.com/yandex-cloud/yandex-ai-studio-sdk/blob/master/.pre-commit-config.yaml) (v0.22.1, 2026-07-15) · конфиг или инструмент · средняя · реконструкция.
- Пример:

```yaml
# .pre-commit-config.yaml (фрагмент). Порог 10 000 КБ - как в Yandex AI Studio SDK.
# Не запускалось: реестр пакетов недоступен из среды сборки.
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v6.0.0
    hooks:
      - id: check-added-large-files
        args: ["--maxkb=10000"]
```

SDK закрепляет `pre-commit-hooks` на `v4.1.0`; в примере стоит актуальный тег `v6.0.0`. Порог SDK рассчитан на его собственные ноутбуки с картинками и звуком (до 8,8 МБ); для репозитория без таких примеров разумнее порог ниже, например 1000 КБ (решение авторов профиля). Если из демонстрационных ноутбуков нужно убирать только служебные метаданные, тот же `nbstripout` запускают для этого каталога с опцией `--keep-output`.

### Y-NB-008 · MUST · Секреты в ноутбуке читать из окружения; значение не печатать и не присваивать обычной переменной
- Проверка: частично: сканер секретов в pre-commit и CI (общее правило о секретах - Y-MLOPS-005 в [mlops.md](mlops.md)); выводы ячеек - ручное ревью.
- Источник: [DataSphere: секреты](https://yandex.cloud/ru/docs/datasphere/concepts/secrets) (2025-04-30) · официальный гайд · высокая; в источнике это совет пользователю DataSphere, профиль поднимает уровень до MUST, потому что вывод ячейки попадает в git вместе с ноутбуком.
- Пример:

```python
# плохо: значение секрета окажется в сохранённом выводе ячейки
token = os.environ["API_TOKEN"]
print(token)

# хорошо: значение уходит только в клиент
client = make_client(token=os.environ["API_TOKEN"])
```

## 5. Git и инструменты

### Y-NB-009 · SHOULD · Каталог `.ipynb_checkpoints` держать в `.gitignore`
- Проверка: строка `.ipynb_checkpoints` в `.gitignore`.
- Источник: [tabm .gitignore](https://github.com/yandex-research/tabm/blob/main/.gitignore) (2025-11-10) · практика, выведенная из репозиториев (10 из 12) · высокая · реконструкция.

### Y-NB-010 · SHOULD · Помечать `*.ipynb` в `.gitattributes` атрибутом Linguist, чтобы JSON ноутбуков не искажал статистику языков репозитория
- Проверка: строка `*.ipynb linguist-vendored` или `*.ipynb linguist-generated=true` в `.gitattributes`.
- Источник: [catboost .gitattributes](https://github.com/catboost/catboost/blob/master/.gitattributes) (HEAD от 2026-10-09); [AsyncReasoning .gitattributes](https://github.com/yandex-research/AsyncReasoning/blob/HEAD/.gitattributes) (2026-05-12) · практика, выведенная из репозиториев (2 репозитория: CatBoost и 1 из 12 в `yandex-research`) · низкая · реконструкция.

Атрибуты действуют по-разному ([документация Linguist](https://github.com/github-linguist/linguist/blob/main/docs/overrides.md), не Яндекс): оба исключают файлы из статистики языков, а `linguist-generated` ещё и скрывает их в диффах GitHub. Для рабочих ноутбуков, которые проходят ревью, подходит `linguist-vendored`; `linguist-generated` - только для демонстрационных, чьи диффы никто не читает. Linguist - инструмент GitHub; действие этих атрибутов в GitLab не проверялось.

### Y-NB-011 · SHOULD · Ноутбук, который правят несколько человек, хранить в паре с текстовым представлением через `jupytext`
- Проверка: `jupytext.toml` с `formats = "ipynb,py:percent"`; хук `jupytext` с `args: [--sync]`.
- Источник: [jupytext: документация по pre-commit](https://github.com/mwouts/jupytext/blob/main/website/src/content/docs/using/pre-commit.md) (v1.19.6, 2026-10-04) · конфиг или инструмент · высокая · не Яндекс.
- Пример:

```yaml
# .pre-commit-config.yaml (фрагмент). jupytext v1.19.6 - не Яндекс.
# Не запускалось: реестр пакетов недоступен из среды сборки.
repos:
  - repo: https://github.com/mwouts/jupytext
    rev: v1.19.6
    hooks:
      - id: jupytext
        args: [--sync]
```

В репозиториях Яндекса `jupytext` не используется (0 из 12). Он решает другую задачу, чем `nbstripout`: ревью идёт по файлу `.py`, а `.ipynb` остаётся для запуска. Если в git хранится только текстовое представление, хук не нужен вовсе. Один инструмент на каталог достаточно: для рабочих ноутбуков одного автора хватает `nbstripout`.

### Y-NB-012 · SHOULD · Код ячеек проверять тем же линтером и форматтером, что и модули, и включать ноутбуки в общую команду проверки
- Проверка: `ruff check` и `ruff format --check` обрабатывают `.ipynb` без дополнительных настроек (проверено локально: ruff 0.16.8); проверка орфографии - `typos <файл>.ipynb`.
- Источник: [DataSphere: проект](https://yandex.cloud/ru/docs/datasphere/concepts/project) (2026-06-15) · официальный гайд · средняя; [tabm Makefile](https://github.com/yandex-research/tabm/blob/main/Makefile) (2025-11-10) · конфиг или инструмент · низкая · реконструкция.

DataSphere предустанавливает расширение форматирования ячеек (black, isort); tabm включает `typos example.ipynb` в цель `lint`. Общая команда проверки описана в Y-ML-008.

## 6. Оформление ноутбука

### Y-NB-013 · SHOULD · Демонстрационный ноутбук начинать с установки недостающих пакетов и фиксации сидов
- Проверка: ручное ревью.
