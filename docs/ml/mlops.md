# MLOps: профиль Яндекса

> Данные актуальны на 2026-10-09.

Письменного стандарта MLOps у Яндекса в открытом доступе нет. О внутреннем трекинге экспериментов, реестре моделей, мониторинге качества, дрейфе и откате моделей публичных данных не найдено. Публично доступны три слоя, и этот документ их не смешивает: (а) письменные источники - документация Yandex DataSphere, CatBoost и Yandex AI Studio SDK, туториалы Yandex Cloud, статьи о YTsaurus (2025) и Нирване (2018); (б) реконструкция по открытым репозиториям с выборкой и долей; (в) общепринятые практики с пометкой «не Яндекс» там, где у Яндекса пусто. Из 23 правил ниже пять прямо сформулированы в письменных источниках Яндекса, двенадцать - реконструкция, шесть - «не Яндекс».

Области идентификаторов: `Y-MLOPS` (этот документ), `Y-LIB` ([libraries.md](libraries.md)), `Y-ML` ([project-structure.md](project-structure.md)), `Y-NB` ([notebooks.md](notebooks.md)), `Y-REPRO` ([reproducibility.md](reproducibility.md)). Структура проекта, ноутбуки, сиды, фиксация окружения и трекинг экспериментов разобраны в соседних документах и здесь не повторяются.

Как читать строку «Источник»: тип источника описывает сам источник; пометка «не Яндекс» означает, что это не правило и не практика Яндекса; пометка «реконструкция» означает, что правило сформулировано авторами профиля по наблюдениям, а в источнике нормой не названо. Туториалы Yandex Cloud и документация DataSphere написаны для внешних пользователей облака: они показывают, что Яндекс рекомендует клиентам, а не как устроена работа внутри компании.

## 2. Версионирование данных и моделей, большие файлы

**(а) Письменные источники.** Документация DataSphere ограничивает загрузку через интерфейс 100 МБ и рекомендует брать больший объём из сетевых хранилищ и баз данных; с 2026-04-20 новые датасеты в DataSphere создавать нельзя, вместо них рекомендованы файловые хранилища ([проекты](https://yandex.cloud/ru/docs/datasphere/concepts/project), 2026-06-15). Модель в DataSphere - отдельный ресурс; версионирование моделей на странице не описано ([модели](https://yandex.cloud/ru/docs/datasphere/concepts/models/), 2025-04-30). В открытой версии YTsaurus датасет и веса лежат в Кипарисе (Cypress), то есть внутри самой платформы ([Хабр, 2025-12-25](https://habr.com/ru/companies/yandex/articles/979336/)). Версии моделей в туториале Yandex Cloud ведёт GitLab Model Registry, запись идёт через MLflow Python API ([туториал](https://yandex.cloud/ru/docs/architecture/mlops-in-managed-gitlab), 2026-10-01). DVC и Git LFS в этих источниках не упоминаются; об их использовании в Яндексе - публичных данных не найдено.

**(б) Реконструкция.** Во всех 12 просмотренных репозиториях `yandex-research` данные и веса в git не лежат: README даёт команду скачивания с Hugging Face или Kaggle (например, `uvx tabred download`). При этом небольшие текстовые артефакты экспериментов коммитятся, и помногу: в `tabm` опубликовано 17,7 тыс. TOML-конфигов и 21,2 тыс. JSON-отчётов. Порог размера файла задан в одном репозитории - Yandex AI Studio SDK: `check-added-large-files --maxkb=10000`.

**(в) Не Яндекс.** DVC хранит в git маленький файл-указатель, а данные - в удалённом хранилище. Git LFS заменяет большие файлы текстовыми указателями внутри git, а содержимое держит на сервере. GitHub предупреждает о файлах больше 50 МиБ и отклоняет файлы больше 100 МиБ ([GitHub Docs](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github), проверено 2026-10-09); лимиты GitLab в этом исследовании не проверялись - уточните их для своего инстанса.

### Y-MLOPS-001 · SHOULD · Данные, веса и чекпойнты хранить вне git; в репозитории держать код, конфиги запусков, небольшие текстовые отчёты и команды получения данных
- Проверка: частично: `.gitignore` для каталогов данных и весов, хук `check-added-large-files` (Y-MLOPS-002); остальное - ручное ревью.
- Источник: [tabpack README](https://github.com/yandex-research/tabpack/blob/HEAD/README.md) (2026-08-13); [tabm/paper/README.md](https://github.com/yandex-research/tabm/blob/main/paper/README.md) (2025-11-10) · практика, выведенная из репозиториев (12 из 12 по README) · средняя · реконструкция.
- Пример:

| В git | Вне git |
|---|---|
| код, `pyproject.toml`, lock-файл | сырые и обработанные данные |
| конфиг запуска, `report.json` и маркер состояния (Y-ML-009 - Y-ML-011) | веса, чекпойнты, квантованные пулы |
| команды скачивания данных в README | логи TensorBoard, кеши |
| файлы-указатели DVC (Y-MLOPS-003) | архивы и дампы |

### Y-MLOPS-002 · SHOULD · Ограничивать размер добавляемого файла хуком `check-added-large-files` с явным порогом
- Проверка: `pre-commit`, хук `check-added-large-files` (аргумент `--maxkb`); тот же хук в CI.
- Источник: [yandex-ai-studio-sdk, .pre-commit-config.yaml](https://github.com/yandex-cloud/yandex-ai-studio-sdk/blob/master/.pre-commit-config.yaml) (v0.22.1, 2026-07-15) · конфиг или инструмент · средняя · реконструкция. Уровень SHOULD, хотя в источнике хук выполняется в CI: он найден в одном репозитории, а в 12 репозиториях `yandex-research` pre-commit не используется.
- Пример:

```yaml
# .pre-commit-config.yaml (фрагмент)
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v6.0.0            # в yandex-ai-studio-sdk - v4.1.0
    hooks:
      - id: check-added-large-files
        args: ['--maxkb=10000']   # порог из yandex-ai-studio-sdk
```

В SDK порог равен 10 000 КБ, значение хука по умолчанию - 500 КБ. Порог выбирает команда; исключения оформляются через DVC или Git LFS, а не повышением порога. По умолчанию хук смотрит только файлы, добавляемые в индекс; для проверки всего дерева в CI ему нужен аргумент `--enforce-all`.

### Y-MLOPS-003 · SHOULD · Версию набора данных фиксировать указателем в git, а сами данные держать в удалённом хранилище (не Яндекс)
- Проверка: частично: в CI `dvc pull` перед тестами и `dvc status --cloud` (расхождение кеша с удалённым хранилищем); остальное - ручное ревью.
- Источник: [DVC: Get Started](https://doc.dvc.org/start) (версия на странице не указана, проверено 2026-10-09) · официальный гайд · высокая · не Яндекс. У Яндекса: публичных данных не найдено.

`dvc add data/train.parquet` создаёт `data/train.parquet.dvc` и запись в `.gitignore`; в git попадают только они. Переключение версии: `git checkout <rev> -- data/train.parquet.dvc`, затем `dvc checkout`. Идентификатор версии данных записывается в отчёт о запуске (Y-REPRO-011 в [reproducibility.md](reproducibility.md)).

### Y-MLOPS-004 · SHOULD · Git LFS использовать только для немногих бинарных файлов, которые должны лежать рядом с кодом; шаблоны путей хранить в `.gitattributes` (не Яндекс)
- Проверка: `git lfs ls-files` в CI; ручное ревью `.gitattributes`.
- Источник: [git-lfs.com](https://git-lfs.com/) (Git LFS v3.8.0, проверено 2026-10-09) · официальный гайд · высокая · не Яндекс. У Яндекса: публичных данных не найдено.
- Пример:

```gitattributes
# записывается командой: git lfs track "tests/fixtures/*.cbm"
tests/fixtures/*.cbm filter=lfs diff=lfs merge=lfs -text
```

Подходит для тестовых фикстур и небольших эталонных моделей. Для обучающих данных и чекпойнтов Git LFS не заменяет хранилище с версиями (Y-MLOPS-003, Y-MLOPS-013). Шаблон в `.gitattributes` не переводит в LFS файлы, которые уже есть в истории: для них нужен `git lfs migrate import`.

## 3. Что нельзя коммитить

| Что | В git | Где хранить | Чем проверять | Правило |
|---|---|---|---|---|
| Данные, сырые и обработанные | нет | объектное хранилище, база данных, хранилище платформы | `.gitignore`, `check-added-large-files` | Y-MLOPS-001 |
| Веса и чекпойнты | нет | реестр моделей, объектное хранилище | то же | Y-MLOPS-001, Y-MLOPS-013 |
| Секреты: ключи, токены, файлы `.env` | нет | секреты CI и платформы, переменные окружения | сканер секретов | Y-MLOPS-005 |
| Выводы ноутбуков | рабочие ноутбуки - без выводов, демонстрационные - в отдельном каталоге; расхождение с практикой разобрано в [notebooks.md](notebooks.md) | - | `nbstripout` | Y-NB-005 - Y-NB-007 |
| Конфиги запусков, `report.json`, маркеры состояния | да | git | шаблон `.gitignore` | Y-ML-009 - Y-ML-011 |
| Кассеты с записанными ответами API для тестов | да | git, рядом с тестами | - | Y-MLOPS-009 |
| Lock-файл окружения | да | git | - | Y-REPRO-008 |

**(а) Письменные источники.** Секрет в DataSphere - пара «ключ - значение»; значение хранится и передаётся в зашифрованном виде и доступно коду как переменная окружения. Документация советует не выводить значение на экран и не копировать его в обычную переменную ([секреты](https://yandex.cloud/ru/docs/datasphere/concepts/secrets), 2025-04-30). Yandex AI Studio SDK берёт учётные данные из окружения, если аргумент `auth` не задан (правило Y-LIB-017). Секреты в ноутбуках - правило Y-NB-008.

**(б) Реконструкция.** Сканеров секретов в просмотренных репозиториях Яндекса не найдено: в конфиге pre-commit Yandex AI Studio SDK их нет, в `yandex-research` pre-commit не используется (0 из 12).

**(в) Не Яндекс.** gitleaks и detect-secrets - сканеры секретов с готовыми хуками pre-commit.

### Y-MLOPS-005 · MUST · Секреты не коммитить, не печатать и не копировать в обычные переменные; код получает их из хранилища секретов или переменных окружения
- Проверка: частично: `gitleaks` (хук `gitleaks`) или `detect-secrets` (хук `detect-secrets` с файлом `.secrets.baseline`) в pre-commit и CI - оба «не Яндекс»; вывод секрета в лог ловит только ручное ревью.
- Источник: [DataSphere: секреты](https://yandex.cloud/ru/docs/datasphere/concepts/secrets) (2025-04-30) · официальный гайд · высокая; [yandex-ai-studio-sdk, _auth.py](https://github.com/yandex-cloud/yandex-ai-studio-sdk/blob/master/src/yandex_ai_studio_sdk/_auth.py) (v0.22.1) · конфиг или инструмент · высокая. Уровень MUST - решение профиля: источник формулирует совет, но секрет, попавший в историю git, считается скомпрометированным.
- Пример:

```python
from yandex_ai_studio_sdk import AIStudio

# плохо: ключ в коде и в выводе
API_KEY = "<SECRET>"
print(f"using key {API_KEY}")
sdk = AIStudio(folder_id="<FOLDER_ID>", auth=API_KEY)

# хорошо: ключ и каталог SDK берёт из окружения (YC_API_KEY, YC_FOLDER_ID);
# значение секрета в коде не появляется
sdk = AIStudio()
```

## 4. Пайплайны обучения и инференса: принципы

Раздел описывает принципы, а не работу с платформами. О Нирване, YTsaurus и DataSphere сказано только то, что опубликовано.

### 4.1. Что известно о платформах

| Платформа | Источник и статус | Единица работы | Где данные и артефакты | Что даёт повторяемость |
|---|---|---|---|---|
| Нирвана | Статья в блоге Яндекса, 2018-03-12; не обновляется; платформа закрытая | Ациклический граф из блоков-операций; графы от нескольких блоков до нескольких тысяч операций | Хранилище «ключ - значение»; большинство данных временные, объект можно закрепить | Детерминированные блоки при перезапуске берут результат из кеша, в том числе из чужого графа |
| YTsaurus | Статья команды YTsaurus, 2025-12-25; проект открыт под Apache-2.0 с 2023-03-20 | Операция: обучение - vanilla-операция с джобом в Docker-образе; batch-инференс - map-операция над таблицей | Кипарис (Cypress) | Описание операции: образ, команда, ресурсы |
| Yandex DataSphere | Документация Yandex Cloud, страницы 2024-2026 годов | Задание (Job) с файлом `config.yaml`; нода для онлайн-инференса | Хранилище проекта, S3, файловые хранилища | Задание не зависит от ноутбука; повторный запуск (fork) с переопределением параметров |

Факты по платформам:

- **Нирвана.** Платформа управляет вычислительными процессами и не зависит от предметной области. Исполнитель графа не знает содержимого операций: он инициализирует блоки, работает с кешем и следит за зависимостями, а сами операции выполняют внешние процессоры. Перебор гиперпараметров - это запуск сотни копий графа с разными параметрами. Регулярное переобучение - граф, который через API клонирует себя и перезапускается на свежих данных. Производственные процессы со временем переезжают из графического редактора в API ([Хабр, 2018-03-12](https://habr.com/ru/companies/yandex/articles/351016)). Следы 2025-2026 годов косвенные: файл `nirvana_utils.py` с опциональным `import nirvana_dl` и копированием состояния в snapshot path в [urban-traffic-benchmark](https://github.com/yandex-research/urban-traffic-benchmark/blob/HEAD/nirvana_utils.py) (2026-05-14) и переменные «Nirvana operations» в [исходниках документации CatBoost](https://github.com/catboost/catboost/blob/master/catboost/docs/en/presets.yaml).
- **YTsaurus.** По словам руководителя группы ML-инфраструктуры YTsaurus, Яндекс запускает в YTsaurus почти все ML-обучения и batch-инференс; планировщик распределяет CPU и GPU и для распределённого обучения учитывает сетевую топологию. В воркшопе из статьи batch-инференс запускается из YQL-запроса или через Python API, в том числе по расписанию ([Хабр, 2025-12-25](https://habr.com/ru/companies/yandex/articles/979336/)). Чекпойнты, трекинг экспериментов и Нирвана в статье не упоминаются. В навигации [документации YTsaurus](https://ytsaurus.tech/docs/ru/) отдельного раздела про ML нет.
- **DataSphere.** Задания запускают Python-скрипты, bash-скрипты и бинарные файлы вне JupyterLab и не зависят от ноутбуков и запущенных ВМ проекта. `config.yaml` задаёт имя, команду, входы, выходы, окружение и ресурсы. Входные данные и кеш окружения переиспользуются между запусками; данные задания по умолчанию живут 14 дней ([задания](https://yandex.cloud/ru/docs/datasphere/concepts/jobs/), 2026-06-24). Задание можно запустить повторно с другими параметрами - получится клон (fork) ([повторный запуск](https://yandex.cloud/ru/docs/datasphere/concepts/jobs/fork), 2026-06-16). Регулярный запуск строится на Apache Airflow: DAG раз в заданный интервал делает fork задания ([интеграция с Airflow](https://yandex.cloud/ru/docs/datasphere/concepts/jobs/airflow), 2026-06-16).

### 4.2. Принципы, переносимые в обычный репозиторий

Интерпретация: пять принципов ниже - вывод авторов профиля из фактов раздела 4.1. В источниках они нормами не названы.

1. **Пайплайн - граф шагов с явными входами и выходами.** Так устроены Нирвана (блоки и связи по данным) и связка DataSphere Jobs с Airflow. Шаг получает данные только через объявленные входы и отдаёт результат только через объявленные выходы.
2. **Шаг описан декларативно: команда, входы, выходы, окружение, ресурсы.** Так описаны операция YTsaurus и задание DataSphere. Описание лежит в git рядом с кодом; данных и весов в нём нет, есть только ссылки на них.
3. **Детерминированный шаг не пересчитывается.** Нирвана берёт результат из кеша, DataSphere Jobs кеширует входы и окружение. В обычном репозитории тот же эффект дают стадии DVC («не Яндекс»).
4. **Вариация эксперимента - тот же пайплайн с другими параметрами.** В Нирване это копия графа, в DataSphere - fork задания, в `yandex-research` - новый файл конфигурации (Y-ML-009). Регулярное переобучение - тот же пайплайн на свежих данных, а не отдельный скрипт.
5. **Обучение - процесс с состоянием, batch-инференс - функция над таблицей.** В YTsaurus это разные типы операций (vanilla и map). Из этого следуют разные точки входа и разные требования: обучению нужны чекпойнты (Y-MLOPS-007), batch-инференсу - идемпотентность по входной таблице.

### 4.3. Чего нет

Публичных данных не найдено: свежее (после 2018 года) описание Нирваны; версионирование операций Нирваны; прямое описание связи Нирваны и YTsaurus; внутренние трекинг экспериментов и хранилище признаков (feature store); доля ML-нагрузок в YTsaurus в числах.

### Y-MLOPS-006 · SHOULD · Повторяемое обучение и инференс собирать в пайплайн из шагов с явными входами и выходами; каждый шаг описывать декларативно в файле рядом с кодом
- Проверка: частично: наличие файла описания (`config.yaml` задания, `dvc.yaml`, определение пайплайна в CI); запуск пайплайна на малой выборке в CI (Y-MLOPS-010); остальное - ручное ревью.
- Источник: [DataSphere: задания](https://yandex.cloud/ru/docs/datasphere/concepts/jobs/) (2026-06-24) · официальный гайд · средняя · реконструкция; [Хабр: Нирвана](https://habr.com/ru/companies/yandex/articles/351016) (2018-03-12, не обновляется) · книга, статья или доклад · низкая · реконструкция; [DVC: defining pipelines](https://doc.dvc.org/user-guide/pipelines/defining-pipelines) (проверено 2026-10-09) · официальный гайд · высокая · не Яндекс.
- Пример: один шаг обучения в двух описаниях - задание DataSphere Jobs и стадия DVC.

```yaml
# config.yaml - задание DataSphere Jobs (сокращённый пример по документации)
name: train-baseline
desc: Обучение базовой модели по конфигу эксперимента
cmd: >
  python3 scripts/train.py
    --config ${CONFIG}
    --output ${MODEL}
inputs:
  - experiments/baseline.toml: CONFIG
outputs:
  - artifacts/model.cbm: MODEL
env:
  python:
    type: manual
    requirements-file: requirements.txt
cloud-instance-types:
  - g1.1
```

```yaml
# dvc.yaml - тот же шаг как стадия DVC (не Яндекс)
stages:
  train:
    cmd: python scripts/train.py --config experiments/baseline.toml --output artifacts/model.cbm
    deps:
      - scripts/train.py
      - experiments/baseline.toml
      - data/train.parquet
    outs:
      - artifacts/model.cbm
    metrics:
      - artifacts/report.json:
          cache: false
```

Описание одного запуска как задания - правило Y-ML-007 в [project-structure.md](project-structure.md).

### Y-MLOPS-007 · SHOULD · Длительный запуск сохраняет промежуточное состояние во внешнее хранилище и умеет продолжить работу с него
- Проверка: ручное ревью; частично: тест «прервать и продолжить» на малой выборке.
- Источник: [DataSphere: задания](https://yandex.cloud/ru/docs/datasphere/concepts/jobs/) (2026-06-24) · официальный гайд · высокая; [tabm/paper/README.md](https://github.com/yandex-research/tabm/blob/main/paper/README.md) (2025-11-10) · практика, выведенная из репозиториев (флаг `--continue`) · средняя.

Документация DataSphere рекомендует при длительных заданиях сохранять промежуточный результат в объектном хранилище S3; данные самого задания по умолчанию удаляются через 14 дней. Для CatBoost возобновление работает только при запуске в том же каталоге с теми же параметрами (Y-LIB-011). Проверка, что продолжение идёт с тем же конфигом, - Y-REPRO-015.

## 5. CI/CD для ML

**(а) Письменные источники.** Туториал Yandex Cloud описывает цикл на GitLab: эксперимент - это ветка с изменёнными гиперпараметрами и merge request; пайплайн GitLab CI обучает и тестирует модель при создании merge request (ручной job `trigger_train`); параметры, метрики и артефакты запуска пишутся в GitLab Model Experiments через MLflow Python API; удачный запуск продвигается в версию модели в реестре ([туториал](https://yandex.cloud/ru/docs/architecture/mlops-in-managed-gitlab), 2026-10-01). DVC и мониторинг в туториале не упоминаются. В Yandex AI Studio SDK CI на GitHub Actions запускает тесты по матрице Python 3.10-3.14, проверки pre-commit, сборку документации и тест совместимости старого пакета ([tests.yaml](https://github.com/yandex-cloud/yandex-ai-studio-sdk/blob/master/.github/workflows/tests.yaml)).

**(б) Реконструкция.** В общем измерении 25 репозиториев Яндекса GitHub Actions есть у 22, тесты или сборка на pull request запускаются в 19. В исследовательских репозиториях картина обратная: CI нет ни в одном из 12, тесты есть в одном (`tabm`). Ближайший аналог проверки в `yandex-research` - обязательный «быстрый тест» окружения в `tabpack`: `uv run ruff check`, `uv run ruff format --check`, `uv run ty check`. В YaFSDP нет ни GitHub Actions, ни каталога тестов, хотя команда `test` в `justfile` объявлена.

**(в) Не Яндекс.** Тесты данных и моделей, критерии готовности ML-системы к продакшену у Яндекса: публичных данных не найдено. Пробел закрывают статья «The ML Test Score» (Google, 2017) и документ Google Cloud об уровнях MLOps.

**GitHub и GitLab.** Туториал Яндекса опирается на встроенные в GitLab Model Experiments и Model Registry. У GitHub таких встроенных сервисов нет: для трекинга и реестра нужен отдельный сервер MLflow (Yandex Cloud описывает его развёртывание для DataSphere: [туториал](https://yandex.cloud/ru/docs/tutorials/ml-ai/mlflow-datasphere), 2026-09-09). Правила 008-012 от хостинга не зависят.

### Y-MLOPS-008 · SHOULD · В командном ML-репозитории CI на каждый pull request или merge request запускает линтер, проверку типов и тесты теми же командами, что и локально
- Проверка: конфигурация хостинга: обязательные проверки для защищённой ветки (см. [branches.md](../git/branches.md)); наличие workflow GitHub Actions или `.gitlab-ci.yml`.
- Источник: [yandex-ai-studio-sdk, tests.yaml](https://github.com/yandex-cloud/yandex-ai-studio-sdk/blob/master/.github/workflows/tests.yaml) (v0.22.1) · конфиг или инструмент · высокая; практика, выведенная из репозиториев (тесты на pull request - 19 из 25; в `yandex-research` CI - 0 из 12) · средняя · реконструкция.

Уровень SHOULD, потому что это практика большинства, а не письменное правило. Профиль расходится с исследовательскими репозиториями сознательно: они замораживаются после публикации статьи, а командный репозиторий живёт дальше. Единая команда проверки описана в Y-ML-008.

### Y-MLOPS-009 · SHOULD · Тесты кода, который вызывает внешние API моделей, не ходят в сеть: ответы записаны в кассеты, кассеты лежат в git
- Проверка: `pytest --block-network` (плагин `pytest-recording`) в CI.
- Источник: [yandex-ai-studio-sdk, CONTRIBUTING.md](https://github.com/yandex-cloud/yandex-ai-studio-sdk/blob/master/CONTRIBUTING.md); [tox.ini](https://github.com/yandex-cloud/yandex-ai-studio-sdk/blob/master/tox.ini) (v0.22.1) · производный гайд проекта · высокая. В источнике правило обеспечивается флагом в CI; в профиле уровень SHOULD, потому что источник один.

SDK записывает HTTP-ответы через `pytest-recording`, а для gRPC использует собственный перехватчик с флагами `--generate-grpc` и `--regenerate-grpc`. Перед записью кассеты убедитесь, что в неё не попал ключ (Y-MLOPS-005).

### Y-MLOPS-010 · SHOULD · В CI запускать пайплайн обучения на малой выборке: несколько итераций, конечные значения функции потерь, ожидаемые артефакты на выходе (не Яндекс)
- Проверка: отдельный job CI, который запускает точку входа обучения с тестовым конфигом и проверяет наличие и схему `report.json`.
- Источник: [Google Cloud: MLOps - continuous delivery and automation pipelines](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning) (Last reviewed 2024-08-28) · официальный гайд · высокая · не Яндекс. У Яндекса: публичных данных не найдено.

Источник перечисляет проверки CI для пайплайна: юнит-тесты преобразования признаков, сходимость на нескольких примерах, отсутствие NaN, ожидаемые артефакты каждого шага, интеграция шагов. Проверка схемы данных до обучения - в Y-ML-015, тест воспроизводимости на коротком запуске - в Y-REPRO-016.

### Y-MLOPS-011 · SHOULD · Перед регистрацией модели сравнивать её метрики с действующей моделью или базовым порогом на зафиксированной выборке; при провале пайплайн останавливается
- Проверка: шаг пайплайна, который завершается ошибкой при метрике ниже порога; порог и идентификатор выборки лежат в git.
- Источник: [Yandex Cloud: MLOps с ML Registry в Managed GitLab](https://yandex.cloud/ru/docs/architecture/mlops-in-managed-gitlab) (2026-10-01) · официальный гайд · средняя · реконструкция; [The ML Test Score](https://storage.googleapis.com/pub-tools-public-publication-data/pdf/aad9f93b86b7addfea4c419b9100c6cdd26cacea.pdf) (IEEE Big Data 2017) · книга, статья или доклад · высокая · не Яндекс.

Туториал Яндекса показывает обучение и тест модели в CI и запись метрик запуска, но не описывает автоматическое сравнение с порогом - оно взято из ML Test Score (проверка качества перед выкладкой и качество на важных срезах данных).

### Y-MLOPS-012 · SHOULD · Готовность ML-системы к продакшену оценивать по чек-листу ML Test Score и хранить результат рядом с карточкой модели (не Яндекс)
- Проверка: ручное ревью: заполненный чек-лист в репозитории.
- Источник: [The ML Test Score](https://storage.googleapis.com/pub-tools-public-publication-data/pdf/aad9f93b86b7addfea4c419b9100c6cdd26cacea.pdf) (IEEE Big Data 2017) · книга, статья или доклад · высокая · не Яндекс. У Яндекса: публичных данных не найдено.

В чек-листе 28 тестов в четырёх группах по семь: данные и признаки, разработка модели, инфраструктура, мониторинг. Тест, выполненный вручную с записью результата, даёт 0,5 балла, автоматический и регулярный - 1 балл. Итог - минимум из четырёх сумм, поэтому он растёт только при прогрессе во всех группах.

## 6. Реестр моделей, выкладка, мониторинг, дрейф, откат

**(а) Письменные источники.**

- Реестр. Туториал Yandex Cloud ведёт версии моделей в GitLab Model Registry (пример - модель `loan-prediction-demo` версии `0.0.1`). Ресурс «модель» DataSphere сохраняет состояние интерпретатора или результат обучения; форматы - CatBoost (`cbm`, квантованный пул), TensorFlow и Keras, LightGBM, XGBoost, PyTorch, ONNX ([модели](https://yandex.cloud/ru/docs/datasphere/concepts/models/), 2025-04-30).
- Выкладка. Нода DataSphere - изолированная группа ВМ с балансировкой; создаётся из модели (серверная часть - Triton Inference Server) или из произвольного Docker-образа. Алиас публикует сервис и позволяет незаметно для пользователей заменять ноды за ним и убирать устаревшие версии ([Inference](https://yandex.cloud/ru/docs/datasphere/concepts/deploy/), 2026-06-24). CatBoost есть в списке сериализуемых моделей, но в списке моделей для ноды на Triton его нет; для моделей вне списка документация советует ONNX или Docker-образ.
- Мониторинг сервиса. Для инстансов нод включаются проверки состояния по HTTP или gRPC. Ноды и алиасы отдают в Yandex Monitoring частоту запросов, коды ответов и гистограмму времени ответа; можно включить экспорт своих метрик в формате Prometheus ([проверки состояния и мониторинг](https://yandex.cloud/ru/docs/datasphere/concepts/deploy/monitoring), 2024-02-12). Это метрики сервиса: о качестве модели, дрейфе и расхождении данных страница не говорит.
- Эксперименты. В лекции 2017 года описана платформа A/B-тестирования: эксперимент - набор выборок, включая контрольную; перед запуском - автоматические и ручные тесты и экспертное ревью описания, флагов и рисков; при выкатке следят за ключевыми метриками, есть детектор аномалий и аварийное отключение эксперимента ([Хабр, 2017-11-19](https://habr.com/ru/companies/yandex/articles/342704); источник не обновляется).

**(б) Реконструкция.** В открытых репозиториях Яндекса кода выкладки и мониторинга моделей нет; долей здесь быть не может.

**(в) Не Яндекс.** MLflow Model Registry: зарегистрированная модель, её версии, алиасы и теги. Определения расхождения и дрейфа и перечень проверок - в материалах Google.

**Чего нет.** Публичных данных не найдено: внутренний реестр моделей Яндекса; мониторинг качества моделей; детекция дрейфа; процедуры отката моделей; механизм распределения трафика между нодами за алиасом DataSphere.

### Y-MLOPS-013 · SHOULD · Модель, которая уходит дальше эксперимента, регистрировать в реестре: версия, ссылка на запуск с параметрами и метриками, ссылка на артефакт
- Проверка: частично: шаг CD, который публикует модель только из реестра по версии; остальное - ручное ревью.
- Источник: [Yandex Cloud: MLOps с ML Registry в Managed GitLab](https://yandex.cloud/ru/docs/architecture/mlops-in-managed-gitlab) (2026-10-01) · официальный гайд · средняя; [MLflow Model Registry](https://mlflow.org/docs/latest/ml/model-registry/) (MLflow 3, проверено 2026-10-09) · официальный гайд · высокая · не Яндекс.

Уверенность средняя, потому что туториал описывает рекомендацию клиентам облака, а о внутреннем реестре Яндекса публичных данных не найдено. В MLflow версию для воспроизведения адресуют по номеру, а для выкладки - по алиасу, например `models:/MyModel@champion`. Трекинг запусков до регистрации модели - Y-REPRO-013.

### Y-MLOPS-014 · SHOULD · Сервис инференса публиковать под стабильным именем и менять версию модели за ним; предыдущую версию хранить до подтверждения новой
- Проверка: ручное ревью конфигурации выкладки; учебный откат на тестовом стенде.
- Источник: [DataSphere: Inference, алиас](https://yandex.cloud/ru/docs/datasphere/concepts/deploy/) (2026-06-24) · официальный гайд · средняя · реконструкция.

Документация описывает алиас как способ заменять ноды и убирать устаревшие версии незаметно для пользователей. Слов «откат» и «canary» в ней нет: использовать алиас для отката - вывод авторов профиля. Правило отката в общем виде есть в ML Test Score («не Яндекс»): обслуживаемую модель должно быть можно откатить.

### Y-MLOPS-015 · SHOULD · Новую версию модели выкатывать как эксперимент с контрольной группой, заранее названными ключевыми метриками и возможностью аварийного отключения
- Проверка: ручное ревью плана выкладки.
- Источник: [Хабр: как устроено A/B-тестирование в Яндексе](https://habr.com/ru/companies/yandex/articles/342704) (2017-11-19, не обновляется) · книга, статья или доклад · низкая · реконструкция.

Лекция описывает общую платформу экспериментов, а не выкладку ML-моделей; перенос на модели - вывод авторов профиля. Уверенность низкая: источнику девять лет.

### Y-MLOPS-016 · SHOULD · Следить не только за сервисом, но и за данными и предсказаниями: расхождение обучающих и рабочих данных, дрейф, возраст модели, NaN - с порогами и оповещениями (не Яндекс)
- Проверка: ручное ревью: список метрик и порогов в карточке модели; наличие оповещений.
- Источник: [Google ML Crash Course: monitoring pipelines](https://developers.google.com/machine-learning/crash-course/production-ml-systems/monitoring) (обновлено в 2025 году) · официальный гайд · высокая · не Яндекс; [Practitioners guide to MLOps](https://services.google.com/fh/files/misc/practitioners_guide_to_mlops_whitepaper.pdf) (май 2021) · книга, статья или доклад · высокая · не Яндекс. У Яндекса: публичных данных не найдено.

Сервисные метрики (частота запросов, коды ответов, время ответа) DataSphere собирает сама. Расхождение схемы и распределений между обучением и работой, растущий со временем разрыв между обучающими и рабочими данными и изменение связи признаков с целевой переменной платформа не измеряет - это задача команды.

### Y-MLOPS-017 · SHOULD · Код подготовки признаков использовать один и тот же в обучении и в инференсе (не Яндекс)
- Проверка: частично: импорт одного модуля из обеих точек входа; тест паритета (Y-MLOPS-023); остальное - ручное ревью.
- Источник: [Rules of Machine Learning, правило 32](https://developers.google.com/machine-learning/guides/rules-of-ml) (обновлено 2025-08-25) · официальный гайд · высокая · не Яндекс. У Яндекса письменного правила нет; последствия расхождения описывает [CatBoost FAQ](https://catboost.ai/docs/en/concepts/faq#why-float-and-nan-values-are-forbidden-for-cat-features) (CatBoost 1.2.10) · официальный гайд · высокая.

CatBoost хеширует строковое представление категории. Если при обучении значение пришло из матрицы как `1.0`, а при применении из файла как `1`, хеши не совпадут и модель молча получит другую категорию (Y-LIB-002). Общий код подготовки убирает такой класс ошибок.

## 8. C++ в ML

**(а) Письменные источники.** Единственный публичный свод правил C++ у ML-проекта Яндекса - [CPP_STYLE_GUIDE.md](https://github.com/catboost/catboost/blob/master/CPP_STYLE_GUIDE.md) в репозитории CatBoost (последняя правка - 2026-09-21) и [дополнения команды CatBoost](https://github.com/catboost/catboost/blob/master/catboost_command_style_guide_extension.md) (не обновляются с 2023-12-01). Сами правила стиля разобраны в [C++-профиле](../languages/cpp.md). Это общий стиль Аркадии, а не стиль для ML: типы с префиксом `T`, интерфейсы `I`, перечисления `E`, функции с заглавной буквы; весь код - C++20, совместимый с CUDA код - C++17 или C++20. Раздел для контрибьюторов называет эти соглашения обязательными ([Coding conventions](https://catboost.ai/docs/en/concepts/development-and-contributions#coding-convention)). Дополнения команды, значимые для кода с данными:

- размеры и индексы - беззнаковые типы фиксированного размера, по умолчанию 64-битные: библиотека работает с потенциально большими данными (Y-ML-018);
- порядок параметров функции - входные, входно-выходные, выходные; входно-выходные и выходные передаются по указателю;
- длина строки - до 110 символов;
- к булеву литералу в вызове - комментарий с именем параметра.

Правила применения моделей из C++ есть только в документации CatBoost: библиотека применения с потокобезопасным C API (Y-LIB-010), экспорт модели в автономный код C++, который требует C++11 ([документация](https://catboost.ai/docs/en/concepts/c-plus-plus-api_applycatboostmodel)), тесты C++-библиотек в подкаталогах `ut` рядом с кодом ([Run tests](https://catboost.ai/docs/en/concepts/development-and-contributions#run-tests)). Раскладка C++-кода и выделение кода применения в отдельную библиотеку - правила Y-ML-016 и Y-ML-017 в [project-structure.md](project-structure.md).

**(б) Реконструкция.** YaFSDP и просмотренные репозитории `yandex-research` написаны на Python; кода инференса на C++ в них нет.

**Чего нет.** Правила Яндекса для C++-кода инференса и расширений сверх общего стиля Аркадии и документации CatBoost: публичных данных не найдено.

### Y-MLOPS-022 · MUST · C++-код инференса и расширений ML-библиотек писать по общему C++-профилю; отдельного стиля для ML-кода нет
- Проверка: `clang-format` и `clang-tidy` с конфигами профиля ([cpp.md](../languages/cpp.md)); остальное - ручное ревью.
- Источник: [CatBoost: Coding conventions](https://catboost.ai/docs/en/concepts/development-and-contributions#coding-convention) (CatBoost 1.2.10, документация на 2026-10-09) · официальный гайд · высокая; [CPP_STYLE_GUIDE.md](https://github.com/catboost/catboost/blob/master/CPP_STYLE_GUIDE.md) (2026-09-21) · производный гайд проекта · высокая.

Уровень MUST взят из источника: соглашения названы обязательными для вклада в CatBoost. Отдельные дополнения команды сформулированы мягче и вынесены в свои правила, например выбор типов для размеров и индексов - Y-ML-018.

### Y-MLOPS-023 · SHOULD · Паритет предсказаний между средой обучения и средой применения проверять тестом на зафиксированной выборке
- Проверка: тест в CI: модель применяется в обеих средах (например, Python и библиотека применения C++ или ONNX Runtime), предсказания сравниваются с допуском.
- Источник: [CatBoost: ONNX, Specifics](https://catboost.ai/docs/en/concepts/apply-onnx-ml#specifics); [CatBoost FAQ: категориальные признаки](https://catboost.ai/docs/en/concepts/faq#why-float-and-nan-values-are-forbidden-for-cat-features) (CatBoost 1.2.10) · официальный гайд · средняя · реконструкция.

Документация CatBoost перечисляет причины расхождений: экспорт в ONNX работает только с числовыми признаками; метка класса бинарного классификатора в onnxruntime выводится неверно; строковое представление категории при обучении и применении может различаться. Тест паритета - вывод авторов профиля из этих предупреждений, в источнике он не описан.
