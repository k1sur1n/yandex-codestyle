# Яндекс: как оформляются код, git-репозитории и ML-проекты (разделы A-F)

> Данные актуальны на 2026-10-09.

Единого публичного стандарта кода у Яндекса нет: внутри существует общий гайд Аркадии по C++ и «комитеты» по языкам, но наружу правила попадают только вместе с открываемыми проектами - как файлы CatBoost, YTsaurus, YDB, Gravity UI и конфиги инструмента сборки `ya`. Поэтому профиль Яндекса в этом репозитории собран из трёх слоёв - письменных правил команд (C++-гайд в редакции CatBoost, Python-гайд YTsaurus, конфиги Gravity UI, документация YDB), дефолтных конфигов Аркадии из `yandex/yatool` и реконструкции по 25 открытым репозиториям, где каждая реконструкция помечена и снабжена выборкой и долей. Внутри компания работает в монорепозитории Аркадия с собственной VCS Arc, ревью в Arcanum и сборкой `ya make`, а на GitHub живут два разных семейства репозиториев - зеркала Аркадии и проекты, ведущиеся прямо в git, - и образцом для git-профиля служат вторые. По ML письменных правил почти нет: нормы восстановлены из документации CatBoost, DataSphere и AI Studio SDK и из практики `yandex-research`, а всё, чего нет публично, закрыто общепринятыми альтернативами с пометкой «не Яндекс». Все четыре исходные гипотезы о Яндексе подтверждены, но каждая - с уточнением (гипотеза о mapsapi-codestyle - лишь частично), а гипотеза сравнения о том, что ESLint-конфиги Яндекса ушли в архив, для Яндекса опровергнута; сравнение с Google - в [comparison/README.md](../comparison/README.md).

## Метод и ограничения

**Первоисточники.** Исследование опирается на четыре рода публичных источников, в порядке приоритета: (1) файлы открытых репозиториев Яндекса - гайды, `CONTRIBUTING.md`, конфиги линтеров и форматтеров, workflow CI, файлы `a.yaml` и `AGENTS.md`; (2) открытая поставка инструмента сборки [yandex/yatool](https://github.com/yandex/yatool) с дефолтными конфигами стиля и документацией `ya style` и `ya test`; (3) документация продуктов - catboost.ai, ydb.tech, ytsaurus.tech, yandex.cloud, diplodoc.com, aistudio.yandex.ru; (4) статьи и доклады сотрудников на Хабре, HighLoad++, CodeFest и в блогах Яндекса и Yandex Cloud. Поиск вёлся на русском и английском. Пересказы и агрегаторы использовались только как наводки; интервью на сторонних площадках помечены как сторонний источник. Хендбуки Яндекс Образования и материалы Практикума в источники правил не включались: это учебные материалы, а не производственные стандарты.

**Зафиксированные ревизии.** Все ссылки на файлы репозиториев закреплены на коммитах, клонированных 2026-10-09: yandex/yatool `daa9a3c774de905c447227eb7547cfb2e9418746`, catboost/catboost `963da016857b91dc729f6f8c61a5711e608ea1d8`, ytsaurus/ytsaurus `6456ed3d4de2144a605e71d223beb7a9942bb8b9`, ydb-platform/ydb `d9692f89c1dd1605ed8c751416d37740ec8e6bbe`, userver-framework/userver `fa7f95824253d98f35b69a52f566e9a0ed29fdbf` (для разделов C и D - также `5fc4b311b0dcb37ba31e9ae50d6b426e2f6a6b09`), yandex/perforator `9ae889ad6be73d22c9c80a08d2fe25e5c44962ca`; остальные SHA указаны в ссылках раздела A. Код из репозиториев не запускался; конфиги профиля проверены локально на clang-format 18.1.3, clang-tidy 18, ruff 0.16.8, Python 3.13 и Node 22 (без установки пакетов из реестров - npm и PyPI из среды сборки недоступны).

**Измерение 25 репозиториев.** Для раздела C измерены 25 репозиториев из 10 организаций GitHub, у каждого есть коммиты 2026 года в ветке по умолчанию: `ydb-platform/ydb`, `ydb-go-sdk`, `ydb-python-sdk`; `ytsaurus/ytsaurus`, `ytsaurus-k8s-operator`, `ytsaurus-ui`; `catboost/catboost`; `userver-framework/userver`; `yandex/yatool`, `perforator`, `YaFSDP`, `odyssey`, `ch-tools`, `mysync`, `pandora`; `gravity-ui/uikit`, `page-constructor`; `diplodoc-platform/cli`, `transform`; `yandex-cloud/yandex-ai-studio-sdk`, `terraform-provider-yandex`; `datalens-tech/datalens`, `datalens-backend`; `yandex-research/graphland`, `tabred`. Три кандидата исключены как неактивные в 2026 году (`yandex/yandex-tank`, `yandex-research/tabm`, `tabpfn-finetuning`). Репозитории клонировались с глубиной 400 коммитов без содержимого файлов; читались дерево файлов на HEAD, последние 300 коммитов ветки по умолчанию (у шести репозиториев история короче), теги и ветки через `git ls-remote`. Всего разобрано **6602 коммита, из них 5114 сделаны людьми** и не являются merge-коммитами. Заголовки лицензии проверялись по 10 случайным файлам исходников на репозиторий. **Pull request как объекты не измерялись**: GitHub API был недоступен, поэтому число ревьюеров, время до слияния и доля внешних PR неизвестны; процесс ревью описан по документам проектов. Настройки защиты веток без прав администратора не видны и выведены из текстов проектов. При подготовке профиля 2026-10-09 сделаны свежие клоны всех 25 репозиториев: по ним перепроверены варианты README, расположение `CODEOWNERS` и шаблонов, прочитаны все семь `SECURITY.md`, все семь `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md` пяти проектов, шаблоны PR и формы issue.

**Отдельные выборки по областям.** C++ - пять кодовых баз (util, CatBoost, YDB, YTsaurus, userver) с локальным прогоном стокового clang-format по каталогам `util/generic`, `util/system`, `util/string` (424 файла), `catboost/libs/model` (36), `ydb/core/base` (130) и `yt/yt/core/misc` (150). Python - конфиги 17 репозиториев с измерением полноты аннотаций и формата docstring по коду. TypeScript и JavaScript - 16 публичных репозиториев (выборка смещена к Gravity UI: 12 из 16). Дополнительные языки - SDK YDB и Yandex Cloud, Yatagan, DivKit, ytsaurus-spyt. ML - 12 из 59 репозиториев `yandex-research` (шесть принадлежат одной группе табличного и графового DL с общим модулем `lib`, поэтому доли описывают выборку, а не организацию), 18 из 80 ноутбуков-туториалов CatBoost (выборка не случайная), YaFSDP, Yandex AI Studio SDK, 13 карточек моделей и 4 датасета на Hugging Face.

**Письменное правило и реконструкция.** Письменным считается правило, записанное словами в гайде, документации или `AGENTS.md` команды Яндекса либо заданное конфигом, который проект применяет в CI. Реконструкция - наша формулировка практики большинства, выведенная из репозиториев; в профиле она всегда помечена «реконструкция» с указанием выборки и доли (например, «6 из 25 репозиториев») и имеет уровень SHOULD, кроме случаев, где исключений не нашлось вовсе (README и LICENSE - 25 из 25). Из 437 правил профиля Яндекса пометку «реконструкция» несут 120, пометку «не Яндекс» - 92 (подсчёт по индексу правил, 2026-10-09); доли по областям - в разделе B и в [enforcement.md](../docs/enforcement.md). Правила, уровень которых отличается от формулировки источника, объясняют причину в своём тексте; список таких решений вынесен в раздел E.

**Что не удалось проверить.** Текст внутреннего гайда Аркадии по C++ (`docs.yandex-team.ru/arcadia-cpp/cpp_style_guide`) и любые другие внутренние документы, на которые ссылаются открытые файлы; состав, регламент и полномочия комитетов `cppcommittee` и Python Committee; версии линтеров внутри Аркадии (задаются ресурсами Sandbox); состав патчей собственной сборки `ynd-clang-format-18`; требования к сообщениям коммитов и число обязательных одобрений внутри Аркадии; чем ведут трекинг экспериментов и каким реестром моделей пользуются внутри. Пять страниц Хабра не прочитаны из-за ограничения частоты запросов (HTTP 429) и в отчёте не используются: `habr.com/ru/post/712992`, `habr.com/ru/post/512880`, `habr.com/ru/company/yandex/blog/429956` (вторая часть статьи о CI), `habr.com/ru/news/776586`, `habr.com/en/companies/yandex_cloud_and_infra/articles/773870` (о Gravity UI - использована Medium-версия); не открылись также `habr.com/en/articles/841552` и вакансия «Автосборка в DevTools» на career.habr.com. Инструменты, недоступные в среде сборки (pre-commit, commitlint, Stylelint, nbstripout, jupytext, DVC, Git LFS, gitleaks), не запускались: у их конфигов проверены синтаксис и соответствие файлам на закреплённых тегах. Формулировка «публичных данных не найдено» означает, что источник искали и не нашли, а не что его точно не существует.

### B.1. C++

**Что есть публично.** Единого публичного гайда Яндекса по C++ нет. Общий гайд Аркадии существует, но лежит на внутреннем хосте: README каталога `util/` называет свой стиль более строгой версией общего гайда и даёт ссылку на `docs.yandex-team.ru` ([util/README.md](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/util/README.md#L3-L5)). Снаружи видны три независимо поддерживаемых текста одной и той же аркадийной редакции и два отдельных стиля:

- `CPP_STYLE_GUIDE.md` в CatBoost - самый полный и свежий текст; документация CatBoost объявляет его [обязательным](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/catboost/docs/en/concepts/development-and-contributions.md#L274-L278) для контрибьюторов. Это живой документ: между 2023-06 и 2026-07-15 правок не было, затем за два месяца - 18 коммитов, включая переход с C++14 на C++20 и новое правило о завершающем `_` у приватных полей ([коммит](https://github.com/catboost/catboost/commit/3874f154ccdb464319de129e17c59a9129e52b19)). Интерпретация (уверенность средняя): по отсылкам к `/util`, к «svn, git, hg» и к коду 15-летней давности этот файл - публикация общего гайда Аркадии, а дополнения команды CatBoost так и называются «Дополнения к стайлгайду»; прямого утверждения «это копия внутреннего документа» в файле нет.
- `ydb/agents/CODESTYLE.md` (2026-07-20) - те же правила с теми же примерами, но с собственным порядком include и первым правилом «следуй стилю файла, который правишь».
- `util/README.md` - уточнения для util.
- `yt/styleguide/cpp.md` - гайд YTsaurus; он действует в `yt/yt`, `yt/chyt`, `yt/yql`, `library/cpp/yt` и [не распространяется](https://github.com/ytsaurus/ytsaurus/blob/6456ed3d4de2144a605e71d223beb7a9942bb8b9/yt/styleguide/cpp.md#L8-L21) на C++ SDK и util.
- userver письменного гайда не имеет: стиль задан `.clang-format`, `.clang-tidy` и `AGENTS.md`; страницы о стиле кода в исходниках документации userver.tech нет ([оглавление](https://github.com/userver-framework/userver/blob/fa7f95824253d98f35b69a52f566e9a0ed29fdbf/scripts/docs/en/index.md)).

`CONTRIBUTING.md` YTsaurus, YDB и CatBoost о стиле C++ не говорят, у userver этот файл посвящён только CLA. В документации YDB для контрибьюторов есть гайд по стилю документации, но не кода ([каталог](https://github.com/ydb-platform/ydb/tree/d9692f89c1dd1605ed8c751416d37740ec8e6bbe/ydb/docs/en/core/contributor)). Новый класс источников 2026 года - инструкции для ИИ-агентов: именно в них YDB и userver впервые публично записали правила кода.

**Именование: префиксы подтверждены в четырёх кодовых базах из пяти.** `T` (классы, структуры, алиасы), `I` (интерфейсы), `E` (перечисления), `N` (пространства имён) записаны в гайде CatBoost ([L54](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/CPP_STYLE_GUIDE.md#L54)), в гайде YTsaurus ([L39](https://github.com/ytsaurus/ytsaurus/blob/6456ed3d4de2144a605e71d223beb7a9942bb8b9/yt/styleguide/cpp.md#L39)) и видны в коде util, CatBoost, YDB и YTsaurus - например [`THolder`](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/util/generic/ptr.h#L265), [`IOutputStream`](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/util/stream/output.h#L22), [`EPredictionType`](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/catboost/libs/model/enums.h#L5), [`NActors`](https://github.com/ydb-platform/ydb/blob/d9692f89c1dd1605ed8c751416d37740ec8e6bbe/ydb/library/actors/core/actor.h#L17-L25), [`struct IInvoker`](https://github.com/ytsaurus/ytsaurus/blob/6456ed3d4de2144a605e71d223beb7a9942bb8b9/yt/yt/core/actions/invoker.h#L16-L18). Методы и функции везде в PascalCase, локальные переменные - в camelCase. userver - исключение: [`class Mutex`](https://github.com/userver-framework/userver/blob/fa7f95824253d98f35b69a52f566e9a0ed29fdbf/core/include/userver/engine/mutex.hpp#L28), поля `snake_case_`, константы `kCamelCase`, пространства имён `lower_case` ([.clang-tidy](https://github.com/userver-framework/userver/blob/fa7f95824253d98f35b69a52f566e9a0ed29fdbf/.clang-tidy#L126-L204)). Полная таблица по проектам с примерами - в [cpp.md](../docs/languages/cpp.md), раздел 2; правила - [Y-CPP-020 … Y-CPP-034](../docs/languages/cpp.md).

Две оговорки. Во-первых, правило о `_` у приватных полей (Y-CPP-026) описывает новый код, а не существующий: grep-эвристика по заголовкам находит 0 полей вида `Name_` против 1195 вида `Name` в [`ydb/core/base`](https://github.com/ydb-platform/ydb/tree/d9692f89c1dd1605ed8c751416d37740ec8e6bbe/ydb/core/base) и 0 против 203 в [`catboost/libs/model`](https://github.com/catboost/catboost/tree/963da016857b91dc729f6f8c61a5711e608ea1d8/catboost/libs/model); в util и YTsaurus суффикс используется. Во-вторых, префикс `C` у концептов (Y-CPP-033) нигде не записан: он выведен из кода util и YTsaurus, а в акторной библиотеке YDB концепт назван с `T`.

**Форматирование: один конфиг на четыре репозитория, но собственный бинарь.** Корневой `.clang-format` есть только у userver. В catboost, ydb, ytsaurus и yatool его роль играет дефолт Аркадии [`build/config/tests/cpp_style/.clang-format`](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/config/tests/cpp_style/.clang-format) - побайтно один файл (md5 совпадает в клонах yatool и catboost) с владельцем [`cppcommittee`](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/config/tests/cpp_style/a.yaml): 4 пробела, `ColumnLimit: 0`, `BreakBeforeBraces: Attach`, `PointerAlignment: Left`, `NamespaceIndentation: All`, `InsertBraces: true`, `SortIncludes: false`, `Standard: c++20`. Стоковый clang-format 18.1.3 этот файл читает, но Яндекс форматирует собственной сборкой ([`ynd-clang-format-18`](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/mapping.conf.json#L5274)). Локальный прогон стокового бинаря по `util/generic`, `util/system` и `util/string` дал расхождение в 113 файлах из 424, причём в 101 из них единственное отличие - скобка после списка инициализации конструктора (измерение авторов исследования, не данные Яндекса). Конфиги YT Flow и userver стоковым clang-format 18 не читаются вовсе: в них есть опции собственных сборок (`AfterLambdaCaptureList`, `VanillaContinuationIndenter`). YTsaurus для основного кода конфигов не публикует и [объясняет](https://github.com/ytsaurus/ytsaurus/blob/6456ed3d4de2144a605e71d223beb7a9942bb8b9/yt/styleguide/cpp.md#L29) это тем, что его стиль не выражается средствами clang-format и clang-tidy.

**Статический анализ.** Дефолтный [clang-tidy Аркадии](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/config/tests/clang_tidy/config.yaml) включает пять проверок: две собственные (`arcadia-typeid-name-restriction`, `arcadia-ascii-compare-ignorecase`; их кода в открытых репозиториях нет), `bugprone-use-after-move`, `performance-implicit-conversion-in-loop` и `readability-identifier-naming`. Последняя проверяет регистр классов, полей, функций и макросов и суффикс `_`, но не префиксы: опции `StructPrefix: T`, `EnumPrefix: E`, `NamespacePrefix: N` записаны только в [конфиге YQL](https://github.com/ydb-platform/ydb/blob/d9692f89c1dd1605ed8c751416d37740ec8e6bbe/yql/essentials/.clang-tidy#L432-L439), где сама проверка [выключена](https://github.com/ydb-platform/ydb/blob/d9692f89c1dd1605ed8c751416d37740ec8e6bbe/yql/essentials/.clang-tidy#L389). Префиксы в Яндексе держатся на ревью. Конфиг YQL включает также `bugprone-suspicious-semicolon`, `modernize-use-noexcept`, `misc-use-anonymous-namespace`, `readability-static-definition-in-anonymous-namespace`, `misc-definitions-in-headers`, `modernize-loop-convert` и выключает `bugprone-reserved-identifier`, `modernize-use-trailing-return-type`, `google-build-using-namespace`; в профиль они не добавлены, потому что выходят за текст гайда.

**Принуждение.** Цепочка в экосистеме ya - `ya style` (форматирование) и стилевой тест, включаемый макросом `STYLE_CPP()`. В открытых репозиториях он подключён только для `util`, `yql/essentials`, `ydb/core/nbs` и `ydb/core/tx/columnshard` ([пример](https://github.com/ydb-platform/ydb/blob/d9692f89c1dd1605ed8c751416d37740ec8e6bbe/util/linters.make.inc)). В публичных GitHub Actions ydb, catboost, ytsaurus и userver отдельной задачи clang-format или clang-tidy нет. Команда CatBoost в 2026 году удалила из гайда раздел о `ya style` с пометкой, что он устарел и в CatBoost фактически не используется ([коммит](https://github.com/catboost/catboost/commit/dae4d411c59cfb4fea99744094e0a232d79c27da)). Наш прогон дефолтного формата показывает несовпадение в 33 из 36 файлов `catboost/libs/model`, 127 из 130 в `ydb/core/base` и во всех 150 проверенных файлах `yt/yt/core/misc`. Интерпретация: основной код YDB, YTsaurus и CatBoost стилевыми инструментами публично не проверяется; утверждение «Яндекс форматирует всё через `ya style`» открытыми данными не подтверждается.

**Язык и библиотека.** Все пять кодовых баз на 2026-10-09 целятся в C++20 ([Y-CPP-067](../docs/languages/cpp.md)): гайд CatBoost ([L10](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/CPP_STYLE_GUIDE.md#L10)), значение по умолчанию в сборке ya ([ymake_conf.py](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/ymake_conf.py#L1091)), гайд YTsaurus с заявленным переходом на C++23 ([L27](https://github.com/ytsaurus/ytsaurus/blob/6456ed3d4de2144a605e71d223beb7a9942bb8b9/yt/styleguide/cpp.md#L27)), userver с поддержкой C++20 и C++23. Исключения везде разрешены и служат основным способом сообщать об ошибках (Y-CPP-048); RTTI включён по умолчанию, письменного правила о нём нет. Набор собственных примитивов у каждой базы свой (`yexception`/`Y_ENSURE`, `TError`/`YT_VERIFY`, `UASSERT`), и общий тренд 2024-2026 годов - сближение со стандартной библиотекой: поощрение `TString` из гайда [убрано](https://github.com/catboost/catboost/commit/edafc7519f6c4214b4599acde654d0800aea4298) 2026-07-15, ядро YTsaurus почти целиком на `std::vector`, `std::string`, `std::optional`.

**Тесты.** В Аркадии - собственный фреймворк `library/cpp/testing/unittest` (`Y_UNIT_TEST`), в YTsaurus и userver - GoogleTest, YDB допускает оба. Суффикс `_ut.cpp` общий для util, CatBoost, YDB и YTsaurus; userver пишет `_test.cpp`. Письменных правил о тестах в гайдах нет, см. Y-CPP-064 … Y-CPP-066.

**Изменения за 2-3 года.** Дефолтный `.clang-format` получил `PackConstructorInitializers: Never` (2024-06), один пробел после `//` (2024-08), комментарии у закрывающей скобки namespace (2024-09), обязательные фигурные скобки (2024-11) и переехал на clang-format 18 (2025-01 … 2025-05). userver дважды сменил оформление - в 2024-10 с чистого Google-стиля на 4 пробела и 120 колонок, в 2025-11 на «ya style» - и в версии 3.0 (2026-04) отказался от C++17. Таблица с коммитами - в разделе 10 [cpp.md](../docs/languages/cpp.md).

**C++ в ML** разобран в [разделе F](#f-mle-и-mlops).

**Чего нет.** Текст внутреннего гайда; правила о RTTI, `noexcept`, выборе умных указателей, именах шаблонных параметров и каталогов; состав патчей `ynd-clang-format-18`; публичные доклады или статьи инженеров Яндекса о происхождении префиксов `T`/`I`/`E`/`N` и о работе `cppcommittee` - публичных данных не найдено.

### B.2. Python, Django, FastAPI

**Что есть публично.** Единого документа «Python style Яндекса» нет. Письменный гайд один - [YTsaurus Python Style Guide](https://github.com/ytsaurus/ytsaurus/blob/6456ed3d4de2144a605e71d223beb7a9942bb8b9/yt/styleguide/python.md): 76 строк, опубликован 2025-07-30, действует в четырёх каталогах YTsaurus. Он требует PEP 8 «с лёгким привкусом C++ YT», синтаксис Python 3.8+, строки до 100 символов, двойные кавычки, импорты «от частного к общему», аннотации и docstring у публичных методов. Второй слой - «стандарт Аркадии», который виден не как текст, а как три дефолтных конфига в открытом [yandex/yatool](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/config/tests/py_style/default_configs.json): black с `line-length = 120` и `skip-string-normalization = true`, ruff с `select = ["E4", "E7", "E9", "F", "W"]`, flake8 с `max-line-length = 200`. flake8 запускается автоматически для всех Python-файлов сборки, black и ruff проект включает сам макросами `STYLE_PYTHON()` и `STYLE_RUFF()` ([документация `ya test`](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/docs/ru/test.md#L352-L367)). У файла `ruff.toml` есть формальный ревьюер - группа Python Committee. Третий слой - правила проектов в `AGENTS.md` (SDK YDB): написаны для ИИ-агентов, но фиксируют требования команды - английский язык, Python 3.10+, паритет синхронного и асинхронного API, тесты к каждому изменению.

**Чего нет.** Гайд «Python в Аркадии», правила и состав Python Committee, версии линтеров Аркадии (заданы ресурсами Sandbox), доля проектов с включённым форматтером, правила о структуре пакета и async-стиле - публичных данных не найдено. Хендбуки и курсы Практикума - учебные материалы; как источник правил не использовались.

**Инструменты по проектам (особый пункт брифа).** Измерены конфиги 17 репозиториев; полная таблица - в [python.md](../docs/languages/python.md).

| Проект | Форматтер | Линтер | Типы |
|---|---|---|---|
| YDB (ydb-python-sdk) | black 25.11.0, 120 | flake8 6.1.0 с лимитом 160; pylint вне CI | mypy, без `check_untyped_defs` |
| YTsaurus (yt/python) | не подключён; гайд требует 100 | дефолтный flake8 Аркадии; публичный CI Python не линтует | нет |
| CatBoost (python-package) | конфигов нет | конфигов нет | нет |
| AI Studio SDK | black настроен (120), но не запускается | pyflakes и pylint через pytest; pyupgrade, codespell, pygrep-хуки | mypy через pytest-mypy |

Доли по выборке: ruff как линтер - 11 из 17; flake8 или pyflakes - 5 из 17; black в CI - 5 из 17; `ruff format` настроен в 6 из 17 (в CI проверяется в 2 - testsuite и airflow-provider; с учётом black форматтер проверяется в CI в 7 из 17); mypy - 11 из 17; длина строки 120 - 6 из 17, 88 - 5 из 17; нижняя версия Python ≥ 3.10 - 7 из 17. Интерпретация: чем ближе проект к Аркадии (YTsaurus, CatBoost, тесты YDB), тем слабее автоматический контроль стиля в его открытой части - там действует только мягкий дефолтный flake8.

**Что видно в коде.** Именование по PEP 8 соблюдается везде (отклонений меньше 1 %), префиксов типов из C++ в Python нет. Формат docstring не унифицирован: reST-поля в четырёх SDK, формат Google в YaFSDP и tabm, NumPy в CatBoost; проверку наличия docstring отключили все проекты, где она возможна. Полнота аннотаций следует за инструментом: 99 % в ch-tools и 93 % в datalens-backend, где включён `disallow_untyped_defs`, против 3 % в `yt/python/yt/wrapper`, где аннотаций требует только текст гайда.

**Версии и изменения.** За 2023-2026 годы проекты перешли с flake8 и black на ruff (ch-tools - 2023-08-21, testsuite - 2025-02-14; новые репозитории YDB 2025-2026 годов стартуют сразу на ruff), подняли нижнюю версию Python до 3.10 (ydb-python-sdk снял 3.8 и 3.9 2026-07-06) и добавили mypy (python-sdk - 2024-05-30, ydb-python-sdk - 2026-02-04). В Аркадии ruff появился как опция 2024-01-24 ([коммит 7f5fdeb8](https://github.com/yandex/yatool/commit/7f5fdeb8e8df85c1575ba0a0e3b81b1c022ac68c)), дефолтным форматтером остаётся black.

**Django.** Публичных правил Яндекса - публичных данных не найдено. Активный проект один - [django-ydb-backend](https://github.com/ydb-platform/django-ydb-backend/blob/1c77be98f8044dbfa6b9e45baaca94bd29cdd5de/pyproject.toml#L72-L130), бэкенд базы данных, а не образец приложения; из него взяты три правила ([Y-DJ-001 … Y-DJ-003](../docs/frameworks/django.md)). [django_replicated](https://github.com/yandex/django_replicated) не обновляется с 2020 года. Статья 2020 года подтверждает, что Django исторически был основным веб-фреймворком Python-сервисов Яндекса, но правил стиля не содержит. Остальные двенадцать правил (Y-DJ-004 … Y-DJ-015) - «не Яндекс».

**FastAPI.** Публичных правил и эталонных проектов - публичных данных не найдено. Найден только учебный пример деплоя из одного файла; крупнейший открытый Python-бэкенд Яндекса, datalens-backend, написан на aiohttp и Flask. Все четырнадцать правил ([Y-FAPI-001 … Y-FAPI-014](../docs/frameworks/fastapi.md)) - «не Яндекс».

### B.3. Дополнительные языки

**Отбор.** Из десяти ориентиров брифа опросы 2025-2026 годов оставляют шесть языков для полного разбора, два - для краткого и два исключают. Stack Overflow 2026 вышел 2026-10-06 и уже учтён; JetBrains 2026 и Octoverse 2026 на 2026-10-09 не опубликованы, поэтому для них взяты издания 2025 года. TypeScript и JavaScript лидируют во всех трёх источниках: 43,8 % и 62,0 % респондентов Stack Overflow 2026, первое место TypeScript в Octoverse (2 636 006 контрибьюторов в месяц, +66,63 % за год) и в Language Promise Index JetBrains ([Stack Overflow 2026](https://survey.stackoverflow.co/2026/technology/data), [Octoverse 2025](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/), [JetBrains 2025](https://blog.jetbrains.com/research/2025/10/state-of-developer-ecosystem-2025/)). Java (29,4 → 27,6 %) и C# (27,8 → 27,1 %) - массовые и стабильные, четвёртое и пятое места Octoverse. Go (16,5 %) держит первое место в списке «хотят освоить» у JetBrains - 11 % ([Go Language Trends 2025](https://blog.jetbrains.com/go/2025/11/10/go-language-trends-ecosystem-2025/)). **Rust показал самый заметный сдвиг в Stack Overflow: с 14,8 до 18,0 %**, и остаётся первым по доле желающих продолжать работу с ним. Kotlin (10,8 %) проходит порог в 10 % и растёт по данным JetBrains. PHP (17,7 %) и Ruby (5,8 %) JetBrains относит к языкам в долгосрочном спаде ([раздел о трендах](https://devecosystem-2025.jetbrains.com/tools-and-trends)), поэтому они разобраны кратко. Scala (2,2 %) и Elixir (2,6 %) исключены: меньше 5 % и ни одного верхнего списка. База вопроса о языках в Stack Overflow 2026 (14 099 ответов) вдвое меньше базы 2025 года, поэтому сдвиги меньше 1 п. п. трендом не считаются. Критерий отбора - интерпретация авторов профиля; таблица с числами - в [other.md](../docs/languages/other.md).

**Общая картина.** Ни для одного из десяти языков у Яндекса нет общего публичного гайда. Публичный след внутренних правил - несколько абзацев документации yatool: Java в Аркадии проверяет checkstyle двух уровней, Kotlin - ktlint, Go - `gofmt`, `govet` и собственный `yolint`, TypeScript - ESLint ([test.md, строки 369-381](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/docs/ru/test.md?plain=1#L369-L381) и [строка 472](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/docs/ru/test.md?plain=1#L472)). Сами конфиги этих инструментов, а также исходники `yolint` и `yoimports` не опубликованы. Всё остальное - конфиги отдельных открытых проектов. Плотность следа по языкам разная: TypeScript, Go и Java - несколько активных проектов с настроенными линтерами; Kotlin - две Android-библиотеки; C#, Rust и PHP - по одному SDK YDB; Scala - код без конфигов стиля; Ruby и Elixir - ничего. Отдельный и новый вид источника - файлы `AGENTS.md` и `.agents/rules/` в SDK YDB: короткие правила для ИИ-агентов, которые впервые формулируют требования команды словами.

**TypeScript и JavaScript ([Y-TS-001 - Y-TS-010](../docs/languages/other.md)).** Действующий стандарт - пакеты Gravity UI: `@gravity-ui/eslint-config` 4.3.2, `@gravity-ui/prettier-config` 1.1.1 и замороженный `@gravity-ui/tsconfig` 1.0.0. **Их расширяют 15 из 16 изученных публичных JS/TS-репозиториев**, на актуальный мажор ESLint-конфига перешли 5 из 15. Серверную точку входа `/server` с 11 правилами `eslint-plugin-security` подключают 3 из 16 - nodekit, app-builder, i18n ([server.js](https://github.com/gravity-ui/eslint-config/blob/v4.3.2/server.js#L17-L30)). Два серверных SDK идут своим путём. ydb-js-sdk использует oxlint ^1.66.0 и oxfmt ^0.52.0 с табами, без точек с запятой и с правилом «всегда `let`» ([AGENTS.md](https://github.com/ydb-platform/ydb-js-sdk/blob/abc8955bfc494c220490b04414dff77e572d4c86/AGENTS.md?plain=1#L79-L105)). yandex-cloud/nodejs-sdk построен на `airbnb-base` и `unicorn` под ESLint 8 ([.eslintrc.json](https://github.com/yandex-cloud/nodejs-sdk/blob/e6538f4e7d5dd16406f803a9793fa43f8602be06/.eslintrc.json)). Связка Gravity UI требует ESLint 9: поддержка ESLint 10 на 2026-10-09 не заявлена.

**Java ([Y-JAVA-001 - Y-JAVA-008](../docs/languages/other.md)).** Единственный развёрнутый источник - `ydb.checkstyle.xml` из ydb-java-sdk; тот же файл лежит в ydb-spark-connector, то есть checkstyle настроен в 2 из 4 проверенных кодовых баз. Конфиг запускается через `maven-checkstyle-plugin` 3.6.0 на фазе `test`, цель компиляции - Java 8. Его комментарии прямо объясняют два запрета удобством поиска по коду в монорепозитории, а лимит в 120 символов сопровождает ссылка на внутренний ресурс - оба признака указывают на внутреннее происхождение конфига (интерпретация) ([ydb.checkstyle.xml](https://github.com/ydb-platform/ydb-java-sdk/blob/464e52508487e2380401a7994d85766d98114c39/config/ydb.checkstyle.xml#L48-L54)). Форматтера в CI нет: форматирование задаёт `.editorconfig` с ключами IntelliJ IDEA, что согласуется с тем, что `ya jstyle` в Аркадии основан на форматтере IDEA.

**Kotlin ([Y-KT-001 - Y-KT-007](../docs/languages/other.md)).** Документация называет ktlint, но ни один из двух проверенных открытых проектов его не подключает. Yatagan (Kotlin 1.9.24) хранит в репозитории стиль IDE `KOTLIN_OFFICIAL` и защищает публичный API режимом `explicitApi()` и плагином binary-compatibility-validator 0.13.2. DivKit (Kotlin 2.3.21) использует detekt 2.0.0-alpha.6 с порогами сложности и baseline-файлом в каждом модуле. Уверенность в правилах Kotlin низкая: это два проекта с разными инструментами.

**Go ([Y-GO-001 - Y-GO-010](../docs/languages/other.md)).** Конфиг golangci-lint формата v2 есть в 3 из 5 проверенных репозиториев. Самый полный - у ydb-go-sdk: включены все линтеры, 40 отключены поимённо, форматируют gci, gofmt, gofumpt и goimports, в CI закреплён golangci-lint v2.13.1 ([.golangci.yml](https://github.com/ydb-platform/ydb-go-sdk/blob/c508a149d29de88f7ccb1d3de3c66ba19ad87aec/.golangci.yml#L11-L62)). Рядом лежат письменные правила: английский язык в комментариях и ошибках, реализация в `internal/`, `defer` для мьютексов, тесты с `-race`. Базовые требования - gofmt и `go vet` - подтверждает и документация yatool, поэтому уверенность здесь средняя, а не низкая.

**C# ([Y-CS-001 - Y-CS-007](../docs/languages/other.md)).** Проверка стиля настроена в одном репозитории из трёх. ydb-dotnet-sdk форматирует код утилитой `jb cleanupcode` из пакета JetBrains.ReSharper.GlobalTools 2025.3.2 и запускает ReSharper InspectCode с порогом WARNING; при этом замечания об именовании (`InconsistentNaming`) в CI отключены ([lint.yml](https://github.com/ydb-platform/ydb-dotnet-sdk/blob/1add2779f2595e09f93afbe6c14215102ba3967c/.github/workflows/lint.yml#L57-L99)). Файловая форма `namespace X;` - в 95 из 102 файлов `src/Ydb.Sdk/src`. У CatBoost есть только `.editorconfig`, у yandex-cloud/dotnet-sdk нет ничего.

**Rust ([Y-RS-001 - Y-RS-010](../docs/languages/other.md)).** Источник один - ydb-rs-sdk: rustfmt по умолчанию, clippy с `-D warnings`, `unsafe_code = "forbid"`, редакция 2024, минимальная версия 1.88, линт на Rust 1.96. Содержательные правила - запрет `unwrap` в рабочем коде, приватность по умолчанию, запрет утечки типов `prost` и `tonic` в публичный API - записаны только в `coding-standards.md` и линтером не проверяются.

**PHP и Ruby ([Y-PHP-001 - Y-PHP-005, Y-RB-001 - Y-RB-005](../docs/languages/other.md)).** В ydb-php-sdk CI проверяет только синтаксис (`overtrue/phplint` ^3.0 на PHP 7.2) и запускает PHPUnit на четырёх версиях PHP; инструментов стиля нет. Для Ruby публичных данных не найдено: SDK не существует, Ruby-файлов вне `contrib/` в проверенных монорепозиториях нет. Правила Y-PHP-005 и все Y-RB взяты из гайдов сообщества и помечены «не Яндекс».

**Scala и Elixir.** Код на Scala у Яндекса открыт - ytsaurus-spyt содержит 567 файлов `.scala`, - но конфигов scalafmt, scalastyle или scalafix нет ни там, ни в модуле Spark у CatBoost. Для Elixir публичных данных не найдено.

### B.4. Фронтенд: JavaScript/TypeScript, React, БЭМ, Angular

**Единого стандарта фронтенда Яндекс не публикует.** Публичные источники распадаются на три независимых семейства с разными владельцами: архивный гайд команды API Карт, конфиги Gravity UI и методология БЭМ. Фактический действующий стандарт открытых React-проектов - конфиги Gravity UI: из 16 изученных публичных JS/TS-репозиториев `@gravity-ui/eslint-config` и `@gravity-ui/prettier-config` расширяют 15, а `@gravity-ui/stylelint-config` - все 11 репозиториев со стилями. Единственное исключение - yandex-cloud/nodejs-sdk, собранный на `airbnb-base`, `airbnb-typescript/base` и `unicorn` ([.eslintrc.json](https://github.com/yandex-cloud/nodejs-sdk/blob/e6538f4e7d5dd16406f803a9793fa43f8602be06/.eslintrc.json)). Выборка смещена к Gravity UI (12 репозиториев из 16); о командах вне этой экосистемы публичных данных не найдено.

**mapsapi-codestyle - единственный найденный прозаический JS/TS-гайд Яндекса, и он заморожен.** Репозиторий заархивирован 2023-08-03, но содержательно остановился раньше: JavaScript-часть не менялась с 2018-04-12, TypeScript-часть - с 2019-07-04, а единственный более поздний коммит добавил файл лицензии ([d549f85](https://github.com/yandex/mapsapi-codestyle/commit/d549f85deb7ed7d90e3b302478fc50dd950447e0)). Адреса `github.com/ymaps/codestyle` и `github.com/yandex/codestyle` перенаправляют на него же. Пакетов четыре: `eslint-config-loris` 9.1.0 (peer `eslint ^4.0.0`), `eslint-config-loris-react` 2.0.0, `tslint-config-loris` 6.0.0 и устаревший `jscs-preset-loris` ([README](https://github.com/yandex/mapsapi-codestyle/blob/d549f85deb7ed7d90e3b302478fc50dd950447e0/README.md)). Гайд покрывает только JS и TS: React представлен конфигом без прозы, CSS не затронут. Причина архивации и рекомендованная замена в репозитории не названы - публичных данных не найдено. У источника три лицензии сразу: CC BY-SA 4.0 в тексте `javascript.md`, Apache-2.0 в корневом `LICENSE`, MIT у npm-пакетов.

**JSCS-пресет `yandex` - тот же стиль команды Карт, а не стиль компании.** Пресет добавлен в JSCS 2014-06-04, в день первого коммита гайда и тем же автором ([ac9e471](https://github.com/jscs-dev/node-jscs/commit/ac9e471ed871daf6a9ce9db5f4bb576ee15792bb)), и удалён 2016-02-28 с пометкой, что об этом попросили сотрудники Яндекса ([25b9240](https://github.com/jscs-dev/node-jscs/commit/25b92408ae7f5410bf930e2497814538f034270f)). Его опции - 4 пробела, 120 символов, одинарные кавычки, обязательные точки с запятой - совпадают с более поздним `eslint-config-loris`. Источник используется только для понимания эволюции. Цепочка инструментов по публичным следам: JSCS-пресет `yandex` (2014) → `jscs-preset-loris` (2016) → `eslint-config-loris` и `tslint-config-loris` (2016-2019) → `@yandex-cloud/eslint-config` (2021) → `@gravity-ui/eslint-config` (с 2022-08, [коммит переноса](https://github.com/gravity-ui/stylelint-config/commit/9cd695f23346d64b456fc34333a86e8d00f3e105)).

**Конфиги Gravity UI живы неравномерно и отстают от инструментов на мажор.** ESLint-конфиг развивается: версия 4.0.0 (2025-04-18) перевела его на ESLint 9 и flat config, текущая 4.3.2 вышла 2026-06-30 ([CHANGELOG](https://github.com/gravity-ui/eslint-config/blob/v4.3.2/CHANGELOG.md)). Prettier-конфиг стабилен: пять опций не менялись с 2021-11-12. Stylelint-конфиг 5.0.0 рассчитан на Stylelint 16 (32 правила: 31 включено, `at-rule-no-unknown: null`), базовый tsconfig заморожен с 2022 года. Актуальные мажоры на 2026-10-09 - ESLint 10.12.0 и Stylelint 17.16.0, поддержка которых в конфигах не заявлена; срок поддержки ESLint 9 истёк 2026-08-06 ([eslint.org/version-support](https://eslint.org/version-support/), проверено 2026-10-16; то же в документации angular-eslint), и профиль наследует этот риск от источника. Миграция внутри самой экосистемы не закончена: на v4 и ESLint 9 перешли 5 из 15 репозиториев, остальные остаются на v2-v3 с ESLint 8. Прозаического гайда у Gravity UI нет: слова «following our styleguide» в описаниях пакетов отсылают к документу, который публично не найден. Версии, состав и способ подключения разобраны в [react.md](../docs/frameworks/react.md), раздел 5.

**React-правила существуют только как проектные.** Общий конфиг даёт наборы `eslint-plugin-react` и `eslint-plugin-react-hooks` ([Y-REACT-008, Y-REACT-009](../docs/frameworks/react.md)) и доступность (Y-REACT-013). Остальное - надстройки отдельных репозиториев: запрет `React.FC` (Y-REACT-001; линтером проверяют uikit, components и date-components, в ydb-embedded-ui записан только в `AGENTS.md`), единый стиль импорта React (Y-REACT-005), `<React.Fragment>` вместо сокращения (Y-REACT-011). Письменные правила о структуре компонента, публичном API, i18n и тестах есть в `contribute/` и `AGENTS.md` репозитория uikit и в `AGENTS.md` ydb-embedded-ui (Y-REACT-014 - Y-REACT-020). В 2026 году именно файлы `AGENTS.md` стали в этих репозиториях местом, где записаны инженерные правила. Правил архитектуры приложений (состояние, маршрутизация, загрузка данных) публично нет - публичных данных не найдено; для базовой корректности профиль ссылается на react.dev с пометкой «не Яндекс» (Y-REACT-021).

**От БЭМ в React-коде остались имена классов и принцип «один компонент - одна папка».** Все 10 React-репозиториев со стилями создают классы БЭМ-хелпером с разделителями `__` и `_`; семь используют `@bem-react/classname`, три - стороннюю `bem-cn-lite` ([Y-CSS-001 - Y-CSS-003](../docs/frameworks/react.md)). Остальной БЭМ-стек - i-bem.js, BEMHTML, ENB, уровни переопределения - в проектах Gravity UI не применяется. Вопреки ожиданию, что БЭМ заброшен, репозитории `bem/*` в 2026 году ожили: `bem-core` 5.0.0 вышел 2026-03-22 после паузы с 2018 года, `@bem-react/core` 6.0.0 перешёл на React 19, методология правилась 2026-05-02. Интерпретация: судить по этому о роли БЭМ-стека внутри Яндекса нельзя - правки 2024-2026 годов вносит один мейнтейнер с личного адреса, а публичных заявлений компании о соотношении «Лего», БЭМ и Gravity UI не найдено.

**Angular: публичных данных не найдено.** Ни в одном из 16 репозиториев нет зависимости `@angular/*`, в конфигах Яндекса нет Angular-наборов, страница вакансий фронтенда называет TypeScript, React и Node.js ([yandex.ru/jobs](https://yandex.ru/jobs/professions/frontend-developer)). Профиль даёт общепринятую альтернативу с пометкой «не Яндекс» - Angular Style Guide в редакции 2025 года и `angular-eslint` ([Y-NG-001 - Y-NG-015](../docs/frameworks/angular.md)); форматирование Angular-кода 4 пробелами в профиле - решение профиля ради единообразия, а не практика Яндекса.

## C. Оформление git-репозитория

Правила профиля: [repository.md](../docs/git/repository.md) (Y-REPO-001 … Y-REPO-017, Y-DOC-001 … Y-DOC-011), [commits.md](../docs/git/commits.md) (Y-GIT-001 … Y-GIT-013), [branches.md](../docs/git/branches.md) (Y-BR-001 … Y-BR-012), [code-review.md](../docs/git/code-review.md) (Y-CR-001 … Y-CR-015), [releases.md](../docs/git/releases.md) (Y-REL-001 … Y-REL-013). Шаблоны - в [templates/github](../templates/github) и [templates/gitlab](../templates/gitlab).

**Главный вывод.** Яндекс не публикует общих правил оформления репозитория: нет ни шаблона нового проекта, ни списка обязательных файлов, ни общекорпоративного документа о коммитах, ветках, ревью или релизах в git. Сайт [opensource.yandex](https://opensource.yandex/) перечисляет проекты и программы, но правил не содержит. Поэтому всё, что профиль говорит о репозитории, - реконструкция по открытым проектам; письменные правила существуют только на уровне отдельных команд (YDB, YTsaurus, Gravity UI, Diplodoc, userver).

### C.1. Выборка и два семейства репозиториев

Выборка, метод и ограничения измерения описаны в разделе [«Метод и ограничения»](#метод-и-ограничения): 25 репозиториев из 10 организаций, 6602 коммита (5114 - людей), теги и ветки через `git ls-remote`, PR как объекты не измерялись.

**Два семейства.** Девять из 25 репозиториев несут в корне `.mapping.json` - карту путей «GitHub → Аркадия», а в шести (ytsaurus, catboost, userver, yatool, perforator, terraform-provider-yandex) каждый коммит заканчивается трейлером `commit_hash:`. Это зеркала внутреннего монорепозитория: коммитят в них роботы, PR кнопкой Merge не сливаются, рабочих веток и, местами, тегов нет, GitHub-CI минимален. Внешний PR в зеркале не сливают: его переносят в Аркадию, и он возвращается коммитом с сохранённым автором и строкой `Pull Request resolved:` (такие коммиты есть в 8 из 25 репозиториев). Остальные проекты (Gravity UI, Diplodoc, SDK YDB, MDB-инструменты odyssey, mysync и ch-tools) разрабатываются прямо на GitHub. YDB занимает промежуточное положение: основная разработка идёт на GitHub, а общие каталоги синхронизируются из Аркадии через ветку `rightlib` (по метаданным `.piglet-meta.json` - проект `ydblib`). Интерпретация: образцом для профиля служит второе семейство, потому что только его практики записаны, проверяются инструментом и воспроизводимы без Аркадии.

Раскладка каталогов с исходниками измерена только для YTsaurus (`contrib/`, `vendor/`, `util/`, `library/`, `tools/`, `yt/`); общих правил о ней не найдено.

**Open source.** Лицензия выбирается по экосистеме: npm-пакеты выходят под MIT, серверные продукты и SDK - под Apache-2.0, производные проекты сохраняют исходную лицензию. Копирайт фиксируется один раз в `LICENSE`; пофайловых заголовков нет ни в одном репозитории - это устойчивое отличие от практики Google. CLA Яндекса «подписывается» фразой в описании первого PR, бота нет. При этом три флагмана от CLA отказались: YTsaurus и YDB в 2024 году, CatBoost - 2025-08-02 ([коммит](https://github.com/catboost/catboost/commit/fd18a8a9d3)); причины публично не объяснены. Чужой код в производных от Аркадии проектах лежит в `contrib/` (C, C++, Python) и `vendor/` (Go), а не в `third_party/`; 18 из 25 репозиториев чужой код в дерево не кладут вовсе. Дисклеймера вида «not an officially supported product» у Яндекса нет.

**Командная работа.** `CODEOWNERS` встречается в трёх видах: команды по каталогам (YDB, 271 строка), мейнтейнеры плюс владелец на каждый компонент (uikit), одна строка на весь репозиторий (Diplodoc). О защите веток проекты говорят косвенно: YTsaurus пишет, что формат имён веток обеспечен правилом защиты, YDB - что PR сливается после одобрения участника команды, uikit - что нужно одобрение всех вызванных владельцев. Число обязательных одобрений и состав обязательных проверок - публичных данных не найдено; правила профиля о настройках - Y-REPO-013 и Y-REPO-017.

**Документация.** Флагманские проекты ведут документацию как код на платформе Diplodoc: диалект Markdown YFM, оглавление в `toc.yaml`, переменные в `presets.yaml`, повторно используемые фрагменты в `_includes/`, зеркальные каталоги `en/` и `ru/`. У YDB опубликован гайд по стилю, структуре, жанрам и ревью документации; линтер YFM держит около 35 правил на уровне ошибки, а сборка идёт на каждом PR. YTsaurus описывает свои правила короче, в README каталога документации. Правила профиля - [Y-DOC-001 … Y-DOC-011](../docs/git/repository.md).

### D.1. Аркадия и Arc

**Что такое Аркадия.** Монорепозиторий, в котором хранится «основная часть кода» компании и который вырос из репозитория Поиска; одна из причин его появления - переиспользование кода внутри Яндекса ([Хабр, Липин, 2023-10-10](https://habr.com/ru/companies/yandex/articles/761946/); [ShiftMag, интервью, 2023-08-09](https://shiftmag.dev/mono-repo-infrastructure-yandex-1011/) - сторонний источник). Чтобы начать проект, «достаточно создать папку в монорепозитории» и добавить описание сборки - пользователь сразу получает пул-реквесты и настроенный CI ([Липин, 2023](https://habr.com/ru/companies/yandex/articles/761946/)).

**Языки.** `ya make` поддерживает C++, Python, Java и Go ([docs/ru/README.md](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/docs/ru/README.md#L21)); в конфигурации сборки есть также TypeScript (владелец - Frontend build platform), Kotlin, CUDA, YQL, Lua ([build/conf/ts/a.yaml](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/conf/ts/a.yaml), [custom_lint.conf](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/conf/custom_lint.conf), [styler.py](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/devtools/ya/handlers/style/styler.py#L39-L58)). **Владение.** Файл `a.yaml` в каталоге задаёт владельца-сервис (`service`), заголовок, правила ревью Arcanum (`arcanum.review`), автослияние (`arcanum.auto_merge`) и описание CI (`ci`: секрет, владелец в Sandbox, `actions`, `flows`, `triggers`, `autocheck`) ([build/conf/ts/a.yaml](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/conf/ts/a.yaml), [ide-gradle/a.yaml](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/export_generators/ide-gradle/a.yaml)). Старый механизм - макросы `SUBSCRIBER(...)` в `ya.make`, который читает только Arcanum и который планируют заменить подпиской через `a.yaml`; `NEED_REVIEW()` помечен deprecated ([ymake.core.conf](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/ymake.core.conf#L4640-L4661)). Группы ревьюеров - сущности Arcanum: «approval from one of util members» ([util/README.md](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/util/README.md#L37-L38)). Полная схема `a.yaml` публично не документирована - есть только примеры файлов.

**Сторонний код.** Для `contrib` лицензия обязательна («A license must be prescribed for contribs»), есть `LICENSE_RESTRICTION(ALLOW_ONLY|DENY …)` для ограничения лицензий зависимостей ([license.conf](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/conf/license.conf#L20-L30)); макросы `VERSION(...)` (только информативный) и `ORIGINAL_SOURCE(...)` ([ymake.core.conf](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/ymake.core.conf#L4663-L4669)); стиль в contrib не проверяется (`NO_LINT()`, [test.md](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/docs/ru/test.md#L358)). Обновления делает робот: 516 из 660 коммитов `robot-contrib` в истории yatool имеют вид «Update contrib/… to N» (подсчёт по `git log`, 12 008 коммитов 2023-11-29 … 2026-10-09). Версии Java-библиотек лежат каталогами с номером версии (`contrib/java/junit/junit/4.12`), выбор фиксирует `DEPENDENCY_MANAGEMENT` ([build/docs/readme.md](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/docs/readme.md)) - то есть для Java в дереве допускается несколько версий одной библиотеки. Явной публичной формулировки «правила одной версии» для Аркадии не найдено; косвенные признаки единой версии для C++ и Python - один каталог на библиотеку в `contrib/libs`, который робот обновляет целиком (интерпретация). Зависимости между каталогами ограничивает `CHECK_DEPENDENT_DIRS(DENY|ALLOW_ONLY …)` ([ymake.core.conf](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/ymake.core.conf#L491-L507)).

**Arc: зачем и как.** До Arc был SVN; в 2016 году начались эксперименты с другими VCS, «сперва выбор пал на Mercurial», на попытку довести его до production ушло полтора года, результат признан неудовлетворительным; git не подошёл, потому что `git status` на импортированном trunk «будет отрабатывать минуты», а стабильной реализации FUSE поверх git не было ([Липин, 2023-10-10](https://habr.com/ru/companies/yandex/articles/761946/)); `git-svn` сконвертировать репозиторий не смог ([Хабр, Arc, 2020](https://habr.com/ru/companies/yandex/articles/482926/), доклад). В 2019 году «появляется новая система контроля версий для пользователей в Arcadia с git-like UX»; фундамент - FUSE вместо селективного checkout, база данных - YDB ([Липин, 2023](https://habr.com/ru/companies/yandex/articles/761946/)). В январе 2020 года Arc пользовались 20 % разработчиков монорепозитория, а источником истины оставался SVN: коммит уходил на сервер Arc, создавался пул-реквест в систему ревью, после одобрения патч коммитился в SVN, и конвертер создавал коммит в Arc; напрямую в основную ветку коммитить нельзя, ветки привязаны к пользователю, команды `merge` нет - слияния выполняет сервер; интерфейс повторяет git (`checkout`, `branch`, `commit`, `stash`, `status`, `log`, `reset`), но полной совместимости целью не было ([Хабр, Arc, 2020-01-06](https://habr.com/ru/companies/yandex/articles/482926/), доклад). К 2023 году Arc «поддерживает работу через Git для заранее выбранного набора проектов» ([Липин, 2023](https://habr.com/ru/companies/yandex/articles/761946/)); доклад на HighLoad++ 2023 обещал виртуализацию ФС, лог файла по графу из десятков миллионов коммитов за секунды и сведение интерфейса к трём командам, а программный комитет отметил подготовку Arc к выходу в open source ([аннотация, 2023-11-27](https://highload.ru/moscow/2023/abstracts/10676), доклад) - на 2026-10-09 публичного релиза Arc не найдено. Вакансия 2025 года называет задачи стабилизации, индексов истории, FUSE и «альтернативы модели commit/branch/PR» с сохранением git-like flow ([getmatch, 2025-09-05](https://getmatch.ru/vacancies/27306-razrabotchik-arc-vcs), сторонний источник). Следы в коде `ya`: тип рабочей копии определяется по `.svn`, `.arc/HEAD`, `.hg`, `.git` ([vcs/__init__.py](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/devtools/ya/yalibrary/vcs/__init__.py#L23-L32)), версия - командами `arc info --json` и `arc describe --svn --dirty --first-parent` ([vcsversion](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/devtools/ya/yalibrary/vcs/vcsversion/__init__.py#L256-L262)); внутренние ссылки имеют вид `a.yandex-team.ru/arc/trunk/arcadia/<путь>?rev=<N>` ([ymake.core.conf](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/ymake.core.conf#L472)). Интерпретация: опция `--svn` и ссылки с `?rev=N` показывают, что у коммитов trunk до сих пор есть сквозной номер ревизии в стиле SVN; перешёл ли источник истины с SVN на Arc полностью, публично не сказано. Схема именования веток, правила их жизни, команда `arc pr` - публичных данных не найдено.

**Экспорт на GitHub.** В корне экспортируемых репозиториев лежат `.piglet-meta.json` вида `{"project":"ya","repository":"arcadia"}` (проекты `ya`, `catboost`, `yt`, `ydblib`, `perforator`, `userver`) и `.mapping.json` - таблица «путь на GitHub → путь в Аркадии» ([yatool](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/.mapping.json), [catboost](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/.piglet-meta.json)). Синхронизацию выполняет робот `robot-piglet`; изменения без осмысленного коммита приходят как «Intermediate changes» (451 коммит в yatool). С 2024-09-12 экспортируемые коммиты получают трейлер `commit_hash:<sha>` (первое появление в yatool и userver в один день; в последних 400 коммитах YTsaurus - у 400 из 400). Номера ревизий вычищаются: 1335 коммитов yatool содержат буквальное `rXXXXXX` (подсчёты по `git log`). Для открытой сборки включается флаг `OPENSOURCE=yes` (например, `DISABLE_FLAKE8_MIGRATIONS=yes`, `GO_VET=no`), а для внешних систем сборки есть экспорт `devtools/yexport` с флагами `EXPORT_CMAKE`, `EXPORT_GRADLE` ([opensource.conf](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/conf/opensource.conf#L12-L30)). userver поддерживает две системы сборки, внешние изменения с GitHub переносились в Аркадию, «опыт CatBoost помог» ([Яндекс Карьера, 2023-11-09](https://yandex.ru/jobs/blog/kak-vykhodyat-v-opensors)). YDB устроен иначе: в first-parent-линии основной ветки нет ни одного коммита с `commit_hash:`, 532 из 798 просмотренных коммитов - squash-коммиты PR с суффиксом `(#NNNN)`, 147 - merge-коммиты, а 390 коммитов с `commit_hash:` приходят вливаемыми ветками ([.piglet-meta.json YDB](https://github.com/ydb-platform/ydb/blob/d9692f89c1dd1605ed8c751416d37740ec8e6bbe/.piglet-meta.json); выборка `git clone --depth 400`, 2026-09-18 … 2026-10-09).

### D.2. Код-ревью: Arcanum

**Сервис.** Arcanum - внутренний веб-сервис для работы с репозиторием, аналог GitHub: поиск и навигация по коду, код-ревью, запуск тестов ([infra.yandex.ru/ype](https://infra.yandex.ru/ype); [Яндекс Образование, ≈2019-2020](https://education.yandex.ru/journal/kakie-tekhnologii-yandeks-stroit-dlya-komand-razrabotki): «более 2000 изменений кода» в день). Описание устройства сервиса известно только по этим двум страницам и статьям; интерфейса никто публично не показывал.

**Правила ревью задаются декларативно в `a.yaml`, по каталогам** (все факты - по файлам yatool на 2026-10-09). Поля: `auto_assign`, `min_approvers_count`, `groups` (имя группы → роль, например `cppcommittee:consultant`), `rules` с фильтрами `subpaths` и `authors`, у ревьюера - `assign` (сколько человек назначить) и `ship` (сколько одобрений от группы нужно), `ignore_self_ship`, `disabling_policy: denied` ([cpp_style/a.yaml](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/config/tests/cpp_style/a.yaml), [yaml_style/a.yaml](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/config/tests/yaml_style/a.yaml)). Правила могут зависеть от автора: «если изменения от команды ya_make, то ревью на них…, если от стороннего - ревью на FBP» (`authors: "!ya_make:developer"`, `assign: 999`, `ship: 1`) ([build/conf/ts/a.yaml](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/conf/ts/a.yaml)). Автослияние: `auto_merge: enabled: true` с условием `type: comment_issues_closed` ([ruff/a.yaml](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/config/tests/ruff/a.yaml)). CI-действия на PR: `triggers: - on: pr` с `required: always` и фильтром путей, вариант `on-demand: true`, секция `autocheck: fast-targets`; CI-поток может оставлять обязательный к закрытию комментарий (`issue: true`): «Любые правки в Cython должны также менять CYTHON_FAKEID…» ([contrib/tools/cython/a.yaml](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/contrib/tools/cython/a.yaml)). Интерпретация (уверенность средняя): слово `ship` подтверждает, что одобрение в Arcanum называется «ship»; `assign` и `ship` разведены - группу можно назначить для информирования (`ship: 0`) или требовать от неё одобрения (`ship: 1`); в `cpp_style/a.yaml` у комитета `ship: 0` при `min_approvers_count: 1`, то есть комитет обязательно назначается, а одобрить может один любой ревьюер. Документации полей нет, трактовка выведена из примеров.

**Единственный опубликованный командный регламент - у `util`** ([util/README.md](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/util/README.md#L33-L60), состояние на 2026-10-09): для коммита нужно одобрение одного из участников группы `util`; без ревью допускаются исправления грамматики и опечаток, приведение кода к стайлгайду и откат ломающего изменения, попавшего в trunk; если ответа нет 1-2 рабочих дня - вежливо напомнить в чате; запрос считается устаревшим, если автор не обновлял его 3 месяца или ушёл из компании, и ревьюеры могут его закрыть; доводить ревью до конца - обязанность автора. Эти пункты перенесены в профиль как [Y-CR-007, Y-CR-008, Y-CR-010](../docs/git/code-review.md).

**Проверки до и после коммита - модель сдвинулась к обязательным.** 2018: прекоммитные проверки «запускаются добровольно», «для особо важных проектов» обязательны; после коммита на каждое изменение запускаются сборки, style-проверки, small- и medium-тесты, остальные - периодически; при поломке запускается поиск ломающего коммита (для diff-тестов - бинарный), уведомления получают владельцы теста и автор; мигающие тесты получают флаг `muted`, все тесты запускаются дважды ([Хабр, CI, 2018-11-08](https://habr.com/ru/companies/yandex/articles/428972/)). Макрос `NEED_CHECK()` блокирует коммит прекоммитной проверкой и автоматически вливает его в trunk, «only if there is no new broken build targets»; по умолчанию макрос отключён ([ymake.core.conf](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/ymake.core.conf#L4622-L4626)). 2020: в Arc напрямую в trunk коммитить нельзя, только через пул-реквест ([Хабр, Arc](https://habr.com/ru/companies/yandex/articles/482926/), доклад). 2021: автотесты запускаются в прекоммитных проверках на кластере распределённой сборки, CI использует Sandbox как рантайм ([Хабр, Sandbox](https://habr.com/ru/post/544842), доклад). 2026: «сначала обязательные тесты и статанализаторы, затем ручное ревью»; первого комментария человека «можно было ждать несколько часов», NeuroReview комментирует через 2-3 минуты, подключение добровольное, принимается около 30 % его замечаний, «финальное слово и ответственность за код остаются за человеком»; распределение принятых замечаний людей - 31 % бизнес-логика, 35 % рефакторинг, 23 % minor, 1,8 % language bug; у NeuroReview - около 50 % бизнес-логика, 16 % language bug ([Хабр, NeuroReview, 2026-10-07](https://habr.com/ru/companies/yandex/articles/1089752/)). Когда именно и для всех ли каталогов проверки стали обязательными, публично не сказано. Откаты на практике: 243 из 12 008 коммитов yatool (2,0 %) начинаются с «Revert», «Rollback» или «Откат» (подсчёт по `git log`). Обязательно ли ревью для любого изменения в Аркадии, число одобрений по умолчанию, очередь слияния и поведение при конфликте - публичных данных не найдено; аналога readability-сертификации Google не найдено.

### D.3. Требования к коммитам

Универсального публичного правила оформления сообщений коммитов в Аркадии нет - публичных данных не найдено. Что видно по экспортированным историям (это практика, а не регламент):

- **yatool, вся история** (12 008 коммитов, 9170 человеческих и 2838 от роботов): префикс-ключ тикета (`YT-28451: …`) - у 1138 человеческих коммитов (12,4 %), почти все - очередь `YT` (1083); кириллица в заголовке - 244 (2,7 %); медианная длина заголовка 46 символов, 83 % заголовков ≤ 72 символов. Доля Conventional Commits - 138 коммитов; база этого процента в заметках неясна (1,1 % от всех или 1,5 % от человеческих), поэтому число приводится без доли.
- **YTsaurus**, последние 400 коммитов (2026-09-30 … 2026-10-09): ключ тикета у 135 (34 %). Интерпретация: ключ тикета в заголовке - соглашение отдельных команд (YT), а не правило всей Аркадии: в коде самой команды ya make он почти не встречается.
- **userver**, коммиты 2026 года (1214): 95,6 % начинаются с типа и области («feat tests: …», `fix`, `cc`, `refactor`, `bug`), в теле - трейлер `Tests: …`. Соглашение командное.
- **Тело коммита - это описание PR**: в 2026 году у 973 из 2417 человеческих коммитов yatool есть тело помимо трейлера; встречается Markdown и HTML. С 2025-03-05 в телах встречается блок `<section id="quibbler-autodescription">` с подписью «Autodescription by Yandex Code Assistant» (85 коммитов в yatool; 70 из 2417 человеческих коммитов 2026 года) - след ИИ-помощника, описанного в [статье 2024-09-12](https://habr.com/ru/companies/yandex/articles/841436/).
- **Тикет как обязательный аргумент** встречается в макросах: `KTLINT_BASELINE_FILE(ktlint-baseline.xml "https://st.yandex-team.ru/REMOVE-BASELINE-1")` - файл исключений линтера привязывается к тикету на его удаление ([java.conf](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/conf/java.conf#L2923-L2927)).
- **Письменные правила о коммитах** есть только проектные: CatBoost - «Commits that fix style should be separate from commits that change functionality» и не менять стиль в строках, которые не трогаешь, потому что «every line has an author» ([CPP_STYLE_GUIDE.md](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/CPP_STYLE_GUIDE.md#L20-L25)); userver (2026) - не добавлять атрибуцию ИИ-агентов: «no `Generated with ...` lines in PR descriptions and no `Co-Authored-By: <agent>` trailers» ([AGENTS.md](https://github.com/userver-framework/userver/blob/5fc4b311b0dcb37ba31e9ae50d6b426e2f6a6b09/AGENTS.md#L32)).

Единые требования к языку, длине и ключу тикета - публичных данных не найдено; профиль берёт Conventional Commits из GitHub-first проектов (раздел C).

Карта «линтер → дефолтный конфиг» - [py_style/default_configs.json](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/config/tests/py_style/default_configs.json) и [cpp_style/default_configs.json](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/config/tests/cpp_style/default_configs.json). Проектный конфиг выбирается параметром `CONFIG_TYPE` макросов `STYLE_*`, а пользовательские конфиги проверяет «валидатор конфигов» на непротиворечие правилам из отдельного файла ([config_validator/README.md](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/devtools/ya/handlers/style/config_validator/README.md)); в открытом дереве файл правил пуст (`{}`). «Миграции» линтеров - `FLAKE_MIGRATIONS_CONFIG=build/rules/flake8/migrations.yaml`, опции `disable_flake8_migrations` и `disable_jstyle_migrations` ([python.conf](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/conf/python.conf#L276-L282)); сам файл миграций не опубликован. Интерпретация: дефолты заметно мягче «книжных» (flake8 с лимитом 200, `ColumnLimit: 0`, узкий набор правил ruff и clang-tidy), потому что общий дефолт должен проходить на огромном унаследованном дереве, а строгие правила включаются проектно; прямо в источниках это не сказано. Два Python-форматтера с отдельным владельцем `ruff.toml` выглядят как идущая миграция black → ruff; публичного решения о ней не найдено.

**Прочая инфраструктура (по докладам).** Sandbox - кластер выполнения задач общего назначения и хранилище ресурсов с 2008 года: около 200 тыс. ядер, около 1 млн задач в день, 5 дата-центров, рантайм CI ([Хабр, 2021-03-05](https://habr.com/ru/post/544842), доклад); артефакты подключаются макросом `FROM_SANDBOX(resource_id …)` и схемой `sbr://` ([ymake.core.conf](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/ymake.core.conf#L4934-L4944)). DistBuild - кластер распределённой сборки и тестов с планировщиком на базе YT ([Хабр, 2021-07-10](https://habr.com/ru/post/565568), доклад). Testenv - публичных данных не найдено.

### D.5. Кто владеет правилами и как они меняются

Публично видна федеративная модель: общий стайлгайд и дефолтные конфиги с владельцами-«комитетами» по языкам, поверх которых команды держат собственные гайды и конфиги.

- **Комитеты.** Дефолтный `.clang-format` принадлежит сервису `cppcommittee`, ревьюеры - группа с ролью `cppcommittee:consultant` ([cpp_style/a.yaml](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/config/tests/cpp_style/a.yaml)); дефолтный clang-tidy ревьюит тот же комитет ([clang_tidy/a.yaml](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/config/tests/clang_tidy/a.yaml)); `ruff.toml` - `service: committeepython`, `title: Python Committee` ([ruff/a.yaml](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/config/tests/ruff/a.yaml)); JSON-конфиг - `jsoncommittee` ([json_style/a.yaml](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/config/tests/json_style/a.yaml)); YAML-конфигом владеет обычная команда ([yaml_style/a.yaml](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/build/config/tests/yaml_style/a.yaml)). Интерпретация: «комитет» - группа-владелец с ролью consultant, которую Arcanum автоматически назначает на правки дефолтного конфига; состав, регламент и полномочия публично не описаны.
- **Командные надстройки.** util: «all {} must be in K&R style», парный `.cpp` к каждому `.h`, запрет `printf`-подобных функций, для нового кода - юнит-тесты и Doxygen-комментарии ([util/README.md](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/util/README.md#L7-L24)); CatBoost - дополнения (строка ≤ 110, порядок параметров in/inout/out); userver - «у нас пожёстче с наименованиями и bool» ([Хабр, Полухин, 2021-03-16](https://habr.com/ru/companies/yandex/articles/545224/)); YT - собственный гайд для своих каталогов, а для чужого кода «try to follow the conventions used in the code around», без конфигов clang-format и clang-tidy ([yt/styleguide/cpp.md](https://github.com/ytsaurus/ytsaurus/blob/6456ed3d4de2144a605e71d223beb7a9942bb8b9/yt/styleguide/cpp.md#L7-L29)).
- **Как меняется гайд.** «This set of conventions is the result of lengthy debates and mutual compromise. So before fixing anything in it, please approve the changes with everyone involved»; предлагающий правку должен обосновать, что проблема мешает большинству, предложить формулировку и объяснить, как она минимизирует переучивание ([CPP_STYLE_GUIDE.md](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/CPP_STYLE_GUIDE.md#L27-L30)). Авторы «tried to streamline it as much as possible and only specify the issues that negatively affect code readability» ([L29-L30](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/CPP_STYLE_GUIDE.md#L29-L30)). История изменений внутреннего документа недоступна.
- **Старый код.** «One file - one style»; новый стандарт обязателен для нового кода; часть кода написана «15+ years ago» и гайду не соответствует ([CPP_STYLE_GUIDE.md](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/CPP_STYLE_GUIDE.md#L16-L25)).
- **Чем держится соблюдение.** Форматтером: гайд util «not a mandatory», но «a next `ya style .` run in the util folder will undeservedly update authors of some lines of code», поэтому перед коммитом рекомендуется `ya style .` ([util/README.md](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/util/README.md#L25-L28)); style-тестами в CI на каждое изменение ([Хабр, CI, 2018](https://habr.com/ru/companies/yandex/articles/428972/)); ревью - в 2026 году 35 % принятых замечаний людей относятся к рефакторингу и 23 % - к minor ([NeuroReview](https://habr.com/ru/companies/yandex/articles/1089752/)). После утечки 2023 года компания объявила «масштабный аудит всего содержимого репозитория» и создание службы, отвечающей за соответствие кода «принципам и политикам» ([пресс-релиз, 2023-01-30](https://yandex.ru/company/press_releases/2023/30-01-2023)) - это контроль политик, а не стиля.
- **Как правила становятся публичными.** Формального органа, публикующего стайлгайды, в описании выхода в опенсорс нет: инициатива идёт от команд, руководство одобряет, команда готовит исходники, убирает зависимости от внутренних проектов, проходит аудит ИБ и юридические вопросы (товарный знак, CLA) ([Яндекс Карьера, 2023-11-09](https://yandex.ru/jobs/blog/kak-vykhodyat-v-opensors)). Гайды попадают наружу как файлы открываемого проекта (CatBoost, YT, util, yatool). Интерпретация: публичность правил - побочный продукт открытия кода.

### D.7. Что переносится на обычный git-репозиторий, а что имеет смысл только в монорепозитории

Колонка «Практика в Яндексе» - факты со ссылками на D.1-D.5; колонки «Аналог» и «Почему» - интерпретация авторов исследования, а не утверждения источников. Публичных рекомендаций самого Яндекса о переносе практик Аркадии в обычный git-репозиторий не найдено; сам Яндекс формулирует границу схожим образом - опыт `ya make` «strongly integrated into the internal ecosystem and is difficult to alienate» ([README yatool](https://github.com/yandex/yatool/blob/daa9a3c774de905c447227eb7547cfb2e9418746/README.md#L29-L33)).

**Переносится на обычный git-репозиторий**

| Практика в Яндексе (источник) | Аналог в GitHub / GitLab | Почему переносится | Правило профиля |
|---|---|---|---|

**Интерпретация (философия и мотивы).** Публичные источники поддерживают три осторожных вывода, каждый - со средней уверенностью: (1) правила и инструменты подчинены масштабу и скорости потока изменений - аргументы в пользу своих VCS и сборки всегда про производительность на размере Аркадии, а в ревью - автоназначение, автослияние, ИИ-ревью через 2-3 минуты, автоописания PR; (2) единообразие достигается дефолтами инструментов и одной командой `ya style`, а не опубликованным регламентом - гайд util прямо назван необязательным, принуждает форматтер; (3) правил стараются держать минимум - гайд регламентирует только мешающее читаемости, а каждое новое правило должно окупать переучивание; отдельный мотив - забота об авторстве строк (`git blame`), которая объясняет правила «стиль - отдельным коммитом» и «один файл - один стиль». Чего утверждать нельзя: что Яндекс «жертвует читаемостью ради скорости», что ревью «формальное» или что стиль «не важен» - источники этого не говорят; наоборот, в 2026 году больше половины принятых замечаний людей относятся к рефакторингу и мелким правкам. Сравнение с Google по этим пунктам - в разделе G (каталог `comparison/`).

## E. Происхождение и конфликты

### E.1. На какие внешние гайды опираются правила

**C++.** Аркадийный гайд на внешние стайлгайды не ссылается; единственная внешняя ссылка в нём - определение стиля скобок 1TBS. Соглашения с префиксами `T`/`I`/`E`/`N` - собственные; объяснений их происхождения в прочитанных источниках нет. Заимствования видны в других местах: гайд YTsaurus обосновывает знаковые целые ссылкой на раздел [Integer Types](https://google.github.io/styleguide/cppguide.html#Integer_Types) гайда Google, а ссылки на аргументы в комментариях (`|parameter|`) в сообщении [коммита](https://github.com/ytsaurus/ytsaurus/commit/b35ffbaeca0d735c637b10a1f4d0e0e91c0346ca) названы стилем Chromium; конфиги userver и YDB columnshard построены на `BasedOnStyle: Google`. От публичного гайда Google аркадийный вариант отличается по существу: исключения обязательны, а не [запрещены](https://google.github.io/styleguide/cppguide.html#Exceptions); заголовки защищает `#pragma once`, а не [`#define`-guard](https://google.github.io/styleguide/cppguide.html#The__define_Guard); стандартная библиотека в списке include идёт последней, а не [перед своими заголовками](https://google.github.io/styleguide/cppguide.html#Names_and_Order_of_Includes); отступ 4 пробела без предела длины строки; лицензионных заголовков в файлах нет. Гайд ClickHouse использован только как исторически связанный источник (компания отделилась от Яндекса): общие черты с аркадийным стилем - 4 пробела, `#pragma once`, исключения, собственные имена целых типов, каталог `contrib`, префикс `I` у интерфейсов, `T`-имена шаблонных параметров; отличия - скобки на отдельных строках, длина строки 140, `snake_case` для переменных, camelCase с маленькой буквы для функций, классы без `T`. Документального подтверждения заимствований в ту или другую сторону нет; источником правил профиля гайд ClickHouse не служит.

**Python.** Гайд YTsaurus прямо называет базой PEP 8. Дефолт Аркадии - black с двумя отступлениями от его умолчаний: 120 символов вместо 88 и отказ от нормализации кавычек. Сортировка импортов в проектах - isort с профилем black. Формат docstring Google встречается только в исследовательском коде (YaFSDP проверяет его через ruff). Отдельных заимствований из Google Python Style Guide в письменных источниках нет. Django для собственного кода задаёт 88 символов, отдельные группы импортов и раннер тестов; HackSoft (логика в сервисах) расходится с философией Django (логика в модели); FastAPI и его шаблон отключают `B008`.

**Дополнительные языки.** Конфиги Gravity UI - конец цепочки, которую можно проследить по публичным следам: пресет `yandex` для JSCS (2014), `jscs-preset-loris`, `eslint-config-loris` и `tslint-config-loris` команды Карт, затем `@yandex-cloud/eslint-config` (2021) и `@gravity-ui/eslint-config` (с 2022 года). Базовые решения - 4 пробела, одинарные кавычки, точки с запятой, `{a: 1}` без пробелов - прошли через всю цепочку без изменений. yandex-cloud/nodejs-sdk прямо наследует Airbnb. Checkstyle-конфиг YDB построен на стандартных проверках Checkstyle и умолчаниях IntelliJ IDEA и расходится с Google Java Style по двум параметрам: строка 120 символов против 100 и собственные группы импортов со статическими в конце ([Google Java Style, 4.4](https://google.github.io/styleguide/javaguide.html#s4.4-column-limit)). Go-, Rust- и C#-проекты опираются на умолчания экосистемы - gofmt и `go vet`, rustfmt и clippy, форматтер ReSharper, совпадающий с соглашениями .NET, - и добавляют проектные правила. Число 120 как длина строки повторяется в дефолте Аркадии для Python, в checkstyle YDB для Java, в тексте правил ydb-js-sdk и, неявно, в ydb-go-sdk (линтер `lll` не отключён, его умолчание - 120 по [справочному конфигу golangci-lint](https://github.com/golangci/golangci-lint/blob/main/.golangci.reference.yml)); Gravity UI и oxfmt-конфиг того же JS SDK держат 100. Прямого источника, объявляющего 120 общим ориентиром, нет - это интерпретация. Требование писать комментарии, сообщения ошибок и логи по-английски повторяется в правилах SDK YDB на Go, Rust, JavaScript и Python и выглядит общим для команды YDB.

**Фронтенд.** В mapsapi-codestyle внешние гайды не названы, но текст частично совпадает с чужими: список образцов именования (`variableNamesLikeThis`, `ClassNamesLikeThis` и далее) и пример длинной строки повторяют старый Google JavaScript Style Guide для ES5 ([ревизия до удаления](https://github.com/google/styleguide/blob/fc855b4a94f7edab4965c2f6fd913a20af7d225c/javascriptguide.xml)), а раздел об `async` - Effective Dart ([dart.dev](https://dart.dev/effective-dart/usage)). Интерпретация: гайд производен от Google-стиля того периода с собственным форматированием (4 пробела и 120 символов); это подтверждено совпадениями текста, но не заявлением авторов. Конфиги Gravity UI ни на Airbnb, ни на Google не опираются: ESLint-конфиг собран из рекомендованных наборов самих инструментов (`@eslint/js`, `eslint-plugin-jsdoc`, `eslint-plugin-react`, `eslint-plugin-react-hooks`, `eslint-plugin-jsx-a11y`, `eslint-plugin-prettier`); Prettier-конфиг - умолчания Prettier 3 с четырьмя отличиями (`tabWidth: 4`, `printWidth: 100`, `singleQuote: true`, `bracketSpacing: false`); Stylelint-конфиг готовых наборов не расширяет, его правила перечислены вручную. Расхождений между mapsapi-codestyle и Gravity UI меньше, чем ожидалось: оба сходятся в 4 пробелах, одинарных кавычках, точках с запятой, записи `{a: 1}`, запрете модификатора `public` и приведении типов через `as`.

**Репозиторий и git.** Кодекс поведения ydb-go-sdk - адаптация Contributor Covenant 1.4, единственный внешний кодекс в выборке. Лицензионная часть следует обычаям Apache-2.0 и MIT: полный текст в `LICENSE`, строка копирайта; файл `NOTICE` есть только у ydb-go-sdk. Формулировка CatBoost о том, что вклад лицензируется под лицензией проекта, - общепринятая схема «inbound = outbound» (источник проект не называет). Гайд по стилю документации YDB в спорных случаях отсылает к Chicago Manual of Style и Merriam-Webster; линтер YFM переиспользует правила markdownlint (`MD*`) и добавляет свои (`YFM*`); YFM заявляет совместимость с CommonMark. Раскладка `contrib/` и `vendor/` унаследована от Аркадии, где лицензия стороннего кода обязательна, а его линтинг отключается. Проекты, живущие на GitHub, берут готовые внешние соглашения: Conventional Commits 1.0.0 и `@commitlint/config-conventional` (Gravity UI подключает его одной строкой), SemVer 2.0.0 (на него прямо ссылается ydb-go-sdk), release-please и его формат changelog, changie и goreleaser в проектах на Go. От спецификаций отступают в мелочах: у Diplodoc свой список типов с `deps`, у userver - запись без скобок, у ydb-go-sdk - исключения из SemVer для помеченного API. Внутреннее происхождение видно только в зеркалах: ключ тикета в начале заголовка, поля `Tests:` в теле, заголовки на русском. Происхождение общей схемы `SECURITY.md` установить не удалось.

**ML.** Собственных письменных корней мало: документация CatBoost и DataSphere. CatBoost для Python требует PEP 8, для C++ - собственный стайлгайд ([Coding conventions](https://catboost.ai/docs/en/concepts/development-and-contributions#coding-convention)). Имена `fully_shard` и `MixedPrecisionPolicy` в YaFSDP совпадают с API FSDP2 в PyTorch - наблюдение, в README связь не заявлена. Datasheet TabReD следует внешней работе «Datasheets for Datasets». Облачные рекомендации по MLOps построены на чужих инструментах: MLflow, GitLab ML Registry, Triton, ONNX, Apache Airflow. Карточки моделей Яндекса следуют формату Hugging Face Hub, а не структуре «Model Cards for Model Reporting»: разделов о назначении, факторах и этических соображениях в них нет. Реконструированные правила структуры ML-проекта восходят к шаблону одной исследовательской группы (общий модуль `lib`); от Cookiecutter Data Science наблюдаемая раскладка отличается тем, что в центре стоит дерево экспериментов с конфигами и отчётами, а не каталоги данных и ноутбуков. Пробелы закрыты внешними источниками с пометкой «не Яндекс»: Cookiecutter Data Science, nbstripout и jupytext, заметки PyTorch и scikit-learn, MLflow, DVC и Git LFS, Model Cards и Datasheets, ML Test Score.

### E.3. Гайд против инструмента и практики

Там, где записанное правило расходится с тем, что делает инструмент или код, профиль верит инструменту (если он исполняется) либо фиксирует расхождение как наблюдение.

- Гайд YTsaurus требует 100 символов, но форматтер в `yt/python` не подключён и 4,2 % строк длиннее. AI Studio SDK держит секцию `[tool.black]`, но black не запускает, а код на 74 % в одинарных кавычках. Правила для агентов в монорепозитории YDB предписывают `unittest`, а существующие тесты написаны на pytest. В ydb-python-sdk форматтер настроен на 120, а линтер - на 160: это не ошибка, а приём «форматтер задаёт цель, линтер ловит то, что форматтер не смог разбить».
- Гайд CatBoost требует префиксы `T`/`I`/`E`/`N` и суффикс `_`, дефолтный clang-tidy проверяет только регистр и суффикс, а код YDB и CatBoost суффикса не использует вовсе (0 из 1195 и 0 из 203 полей). Стоковый clang-format с конфигом Аркадии переформатировал бы 33 из 36, 127 из 130 и 150 из 150 проверенных файлов трёх кодовых баз - публично стиль этих баз инструментом не проверяется.
- `AGENTS.md` ydb-js-sdk называет лимит 120, конфиг oxfmt - 100; `AGENTS.md` ydb-dotnet-sdk говорит о `dotnet format`, workflow запускает `jb cleanupcode`; `.golangci.yml` yandex-cloud/go-sdk в формате v2, а workflow закрепляет golangci-lint v1.54. Текст правил отстаёт от конфигов.
- YTsaurus UI пишет «предпочитаем rebase», соседние проекты Gravity UI - squash: единого решения нет даже внутри фронтенд-команд. Gravity UI требует формат коммита в гайде, но ограничение длины оставляет на умолчании пакета (100), тогда как фактические заголовки uikit короче (медиана 53). Письменного требования DCO нет нигде, но у odyssey и ytsaurus-k8s-operator `Signed-off-by` стоит в большинстве коммитов. README ytsaurus-k8s-operator всё ещё говорит о CLA, хотя CONTRIBUTING того же репозитория его не упоминает - остаток отказа YTsaurus от CLA.
- Внутренняя картина тоже менялась: в 2018 году прекоммитные проверки были добровольными, в 2026 году статья о NeuroReview описывает обязательные тесты и статический анализ до ручного ревью; когда произошёл переход, публично не сказано.
- В ML профиль строже наблюдаемой практики там, где исследовательские репозитории заведомо не образец: тесты (1 из 12), CI (0 из 12), тексты лицензий стороннего кода (3 из 5 репозиториев с `vendor/`), точные версии в `requirements.txt` (2 из 5).

### E.4. Правила, уровень которых отличается от источника

По CONVENTIONS уровень MUST ставится, когда формулировка источника обязательна или проект проверяет правило в CI; в остальных случаях - SHOULD. Решения, где профиль отступил от этого, и их причины (подробнее - в тексте каждого правила):

- **Поднято до MUST.** Y-PY-001 (форматтер) и Y-PY-031 (аннотации с mypy) - рекомендация заметок исследования: правило работает только с инструментом. Y-REPO-001, Y-REPO-002 - реконструкция, но исключений нет (25 из 25). Y-NB-008 и Y-MLOPS-005 (секреты) - в DataSphere совет, в профиле MUST: утечка секрета в историю git необратима. Y-BR-003 - ограничение Arc, перенесённое на git. Y-GIT-010 - формулировка спецификации Conventional Commits (не Яндекс). Y-REL-005 - поведение release-please. Y-CR-005 - формулировка `AGENTS.md` userver, подкреплённая `util/README.md` и гайдом uikit. Y-REACT-001, Y-REACT-005, Y-REACT-011, Y-REACT-013, Y-REACT-014, Y-CSS-009 - надстройки отдельных репозиториев, которые проверяются их CI или названы «invariants»; заметки предлагали «MUST (проектное)» или SHOULD. Y-MLOPS-022 (C++ в ML по общему профилю) - формулировка CatBoost обязательна для его контрибьюторов, перенос на свой репозиторий - решение профиля. Y-LIB-005 («It is not possible» - констатация), Y-LIB-016 («require» в README YaFSDP, только для примеров 2024 года), Y-LIB-026 (scikit-learn, «never», не Яндекс).
- **Понижено до SHOULD.** Y-CPP-038 (в util и CatBoost обязательно), Y-CPP-047 (в YTsaurus «must»), Y-CPP-051 (в YDB «Never»), Y-CPP-055 (в дополнениях CatBoost «обязательно»), Y-CPP-065 (в YDB TESTS.md повелительно) - правила одного проекта или неаркадийного источника. Y-PY-017, Y-PY-018, Y-PY-022 - в `AGENTS.md` ydb-python-sdk формулировки обязательные, но это один проект. Y-KT-001 - документация yatool обязательна, открытые проекты ktlint не используют. Y-ML-006 - в DataSphere блок «Важно», но за пределами DataSphere правило ничего не ломает. Y-ML-018 - «следует предпочитать» в дополнениях CatBoost. Y-MLOPS-002, Y-MLOPS-009 - в SDK выполняются в CI, но источник один. Y-MLOPS-008 - практика большинства (19 из 25), письменного правила нет. Y-DOC-001, Y-DOC-005 - YDB и YTsaurus описывают это как свой подход, гайд по стилю сам называет себя рекомендациями. Y-REPO-016, Y-REPO-017 - настройки хостинга публично не видны.
- **Перенесённые правила.** Y-CPP-029, Y-CPP-049, Y-CPP-050, Y-CPP-063 переносят `Y_…`/`yexception`/`Y_ASSERT`/`/util` на «своё в проекте» - перенос помечен интерпретацией или реконструкцией; Y-CPP-066 (GoogleTest) - реконструкция, потому что аркадийный unittest вне `ya` не работает; Y-REPO-011 опирается на `license.conf` Аркадии, вне её проверяется только `reuse lint` (не Яндекс); Y-PY-016 переносит `import_test` Аркадии в git-репозиторий.

## F. MLE и MLOps

Правила профиля: [project-structure.md](../docs/ml/project-structure.md) (Y-ML-001 … Y-ML-018), [notebooks.md](../docs/ml/notebooks.md) (Y-NB-001 … Y-NB-014), [reproducibility.md](../docs/ml/reproducibility.md) (Y-REPRO-001 … Y-REPRO-016), [libraries.md](../docs/ml/libraries.md) (Y-LIB-001 … Y-LIB-029), [mlops.md](../docs/ml/mlops.md) (Y-MLOPS-001 … Y-MLOPS-023); шаблоны - [templates/ml/MODEL_CARD.md](../templates/ml/MODEL_CARD.md) и [DATA_CARD.md](../templates/ml/DATA_CARD.md).

**Главный вывод: письменного стандарта нет.** Яндекс не публикует ни стайлгайда для ML-кода, ни свода правил MLOps: публичного документа о структуре ML-проекта, границе «исследование - продакшен», ноутбуках в git, конфигах экспериментов, типизации тензоров, логировании метрик, тестах данных и моделей - публичных данных не найдено. Учебный хендбук ШАД таких глав не содержит и производственным стандартом не является. Нормы есть только там, где их диктует продукт: в документации CatBoost, DataSphere и Yandex AI Studio SDK. Всё остальное восстановлено из трёх слоёв - документации продуктов, конфигов библиотек (YaFSDP, SDK) и практики исследовательских репозиториев (выборка 12 из 59 `yandex-research`, клонированы 2026-10-09; шесть принадлежат одной группе табличного и графового DL с общим модулем `lib`, поэтому доли описывают выборку, а не организацию и тем более не Аркадию) - либо взято из общепринятых практик с пометкой «не Яндекс». Из 48 правил трёх документов о стиле ML-кода только три целиком опираются на формулировку письменного источника Яндекса (Y-ML-006, Y-ML-018, Y-NB-008), шесть целиком взяты из внешних источников, остальные 39 - реконструкция по репозиториям или вывод из документации продуктов (по индексу правил пометку «не Яндекс» несут 11 из 48 - часть из них одновременно реконструкция). Из 23 правил области `Y-MLOPS` пять прямо сформулированы в письменных источниках Яндекса, двенадцать - реконструкция, шесть - целиком «не Яндекс» (по индексу пометку «не Яндекс» несут 11); из 29 правил `Y-LIB` 22 относятся к библиотекам Яндекса и семь - к внешним.

### F.1. Стиль ML-кода

**Структура проекта.** У группы табличного DL раскладка устойчива: каталог скриптов (`bin/` или `scripts/`) отделён от каталога модулей (`lib/` или `src/`) в 7 репозиториях из 12, сторонний код вынесен в `vendor/` в 5 из 12 (тексты лицензий при нём - в 3 из 5), а код статьи живёт в `paper/` отдельно от переиспользуемого пакета в 3 из 12 (tabm, graphpfn, tabred). README [tabpack](https://github.com/yandex-research/tabpack/blob/HEAD/README.md) прямо называет `scripts` каталогом исполняемых файлов, которые никогда не импортируются. Библиотеки устроены иначе: YaFSDP - плоский пакет с приватными модулями, Yandex AI Studio SDK - раскладка `src/` с отдельными `tests/` и `examples/`. CatBoost выгружается из монорепозитория и повторяет раскладку Аркадии: библиотеки в `catboost/libs/<имя>/`, тесты в подкаталогах `ut`. Правила [Y-ML-001 … Y-ML-005](../docs/ml/project-structure.md) и Y-ML-016 … Y-ML-018.

**Граница «исследование - продакшен».** Единственная письменная формулировка - в DataSphere: [задания](https://yandex.cloud/ru/docs/datasphere/concepts/jobs/) запускаются вне JupyterLab, не зависят от ноутбуков и описываются файлом `config.yaml`; страница о среде исполнения просит ставить `if __name__ == "__main__":` у всех точек входа. В исследовательских репозиториях граница проходит иначе - «статья против пакета»: [README tabm](https://github.com/yandex-research/tabm/blob/main/paper/README.md) объявляет реализацию из статьи заменённой пакетом `tabm`. Правил перевода кода в продакшен внутри Яндекса публично нет; CI в выборке нет ни в одном репозитории, тесты - в одном. Правила Y-ML-006 … Y-ML-008.

**Конфиги экспериментов.** Единого формата нет: TOML - 5 из 12, JSON - 1, YAML с OmegaConf - 2, только аргументы командной строки - 4; Hydra, gin и ml_collections не встречаются. Зато у шести репозиториев общий контракт запуска: скрипт получает один конфиг и создаёт рядом каталог результата с `report.json`, а готовый результат без флага не перезаписывается (код, пишущий `report.json`, - в 6 из 12; сами файлы в git - в 4). В четырёх репозиториях отчёты лежат в git (в tabm - 21 214 файлов), и `.gitignore` устроен как белый список: в дереве экспериментов разрешены только конфиги, отчёты и маркеры. Правила Y-ML-009 … Y-ML-011.

**Типизация и docstring.** YaFSDP включает `mypy` в строгом режиме, SDK запрещает `# type: ignore` без кода ошибки, конфиг проверки типов есть в 6 из 12 исследовательских репозиториев. Формат docstring не унифицирован: Google-стиль в YaFSDP и tabm, reST-поля в SDK, NumPy-стиль в CatBoost. Формы тензоров статически не типизирует никто: jaxtyping, torchtyping, beartype и typeguard в выборке не найдены (0 из 12); вместо этого в коде стоят комментарии вида `# (B, K, D)`, а пакет [tabm](https://github.com/yandex-research/tabm/blob/main/tabm.py) описывает формы в разделе `**Shape**` docstring и проверяет размерность входа исключением. Правила Y-ML-012 … Y-ML-015.

**Ноутбуки.** Практика обратна общепринятому совету. Ноутбуки есть в 5 репозиториях из 12 (всего 11 файлов `.ipynb`, из них 2 - копии сторонних репозиториев; из 9 собственных 8 закоммичены с выводами, вплоть до 12,2 МБ на файл); в SDK с выводами все 4 ноутбука, в выборке из 18 туториалов CatBoost (из 80) - 17. Ни `nbstripout`, ни `jupytext`, ни pre-commit в исследовательских репозиториях не настроены (0 из 12; `jupytext` встречается только в `tabred/uv.lock` как транзитивная зависимость `kaggle`); `.ipynb_checkpoints` в `.gitignore` - у 10 из 12; AsyncReasoning помечает ноутбуки `*.ipynb linguist-generated=true`. При этом ноутбуки - тонкие демонстрации: во всех четырёх репозиториях с собственными ноутбуками они импортируют модули проекта. DataSphere документирует [механику очистки вывода](https://yandex.cloud/ru/docs/datasphere/operations/projects/clear-outputs) и [работу с Git](https://yandex.cloud/ru/docs/datasphere/operations/projects/work-with-git), но не связывает их правилом. Профиль делит ноутбуки на демонстрационные (с выводами, как у Яндекса) и рабочие (без выводов, `nbstripout` - не Яндекс): правила [Y-NB-005 … Y-NB-007](../docs/ml/notebooks.md); перенос кода в модули - Y-NB-001 … Y-NB-003; запрет печатать секреты в ячейках - Y-NB-008 (в DataSphere совет, в профиле MUST: вывод ячейки попадает в git). Имена каталогов в профиле (`notebooks/` - рабочие ноутбуки без выводов) расходятся с двумя репозиториями выборки, где в `notebooks/` лежат демонстрации с выводами (AsyncReasoning, tabular-dl-optimizers); это решение профиля, помеченное интерпретацией.

**Воспроизводимость.** Сид выставляется в коде во всех 12 репозиториях, в шести он приходит из конфига; `np.random.seed` - 5 из 12; сиды воркеров из базового сида - 3 из 12; `PYTHONHASHSEED` - 2 из 12; флаг `cudnn.deterministic` включают 9 из 12, строгий режим `torch.use_deterministic_algorithms` - один; хеш коммита в отчёте или аргументах - 3 из 12; сверка конфига с существующим отчётом - 2 из 12; оценка по нескольким сидам в README - 3 из 12. Окружение фиксируют по-разному: `uv.lock` в git - 6 из 12, `requirements.txt` - 5 (точные версии всех зависимостей только у двух), conda - 1. Письменные нормы есть у CatBoost: сид по умолчанию фиксирован ([`random_seed`](https://catboost.ai/docs/en/references/training-parameters/common#random_seed)), [обучение на GPU недетерминировано](https://catboost.ai/docs/en/features/training-on-gpu), значения параметров по умолчанию на CPU и GPU различаются ([FAQ](https://catboost.ai/docs/en/concepts/faq#differencies-between-cpu-and-gpu)), а возобновление из снапшота требует того же каталога и тех же параметров ([Snapshots](https://catboost.ai/docs/en/features/snapshots)). Обещания побитовой воспроизводимости на CPU в документации нет; влияние числа потоков не описано. Правила [Y-REPRO-001 … Y-REPRO-010](../docs/ml/reproducibility.md) и Y-REPRO-015; правил уровня MUST в этом документе нет.

**Метрики и трекинг.** Роль трекера у группы табличного DL играют файлы: `report.json` с полным конфигом и метриками на каждый запуск; TensorBoard используется как локальный лог (6 из 12), `wandb` - в одном репозитории, MLflow - ни в одном. Пользователям облака Яндекс рекомендует другое - [сервер MLflow для DataSphere](https://yandex.cloud/ru/docs/tutorials/ml-ai/mlflow-datasphere). Чем ведут трекинг внутри Яндекса, публично не описано: публичных данных не найдено. CatBoost проверяет собственные результаты тестами с каноническими данными и сравнением с ограниченной точностью ([TensorBoard](https://catboost.ai/docs/en/features/visualization_tensorboard) - для визуализации обучения). Правила Y-REPRO-011 … Y-REPRO-014 и Y-REPRO-016.

### F.2. Правила работы с ML-библиотеками

**CatBoost - самый богатый источник.** Документация прямо запрещает one-hot-кодирование до обучения, требует строковых или целых значений категориальных признаков, описывает подбор числа деревьев через валидационный набор и детектор переобучения, предупреждает о недетерминированности GPU и ограничивает экспорт: ONNX и CoreML работают только без категориальных признаков ([parameter tuning](https://catboost.ai/docs/en/concepts/parameter-tuning), [FAQ](https://catboost.ai/docs/en/concepts/faq), [ONNX](https://catboost.ai/docs/en/concepts/apply-onnx-ml#specifics)). Это правила [Y-LIB-001 … Y-LIB-013](../docs/ml/libraries.md). Уровни взяты из формулировок документации: запреты и условия работы стали MUST, рекомендации - SHOULD. Все якоря сверены с исходниками документации в репозитории. Утверждение о разных форматах снапшотов CPU и GPU есть только в исходниках документации внутри блока для внутренней аудитории - упомянуто в Y-LIB-011 с низкой уверенностью, правилом не сделано.

**YaFSDP: код ушёл вперёд от документации.** README и migration guide описывают API 2024 года - класс `YaFSDP(...)` с явным списком шардируемых модулей. Пакет с 2025-01-28 экспортирует функцию `fully_shard`, а старые файлы исключены из собственных проверок ruff и mypy ([`__init__.py`](https://github.com/yandex/YaFSDP/blob/HEAD/ya_fsdp/__init__.py), [migration guide](https://github.com/yandex/YaFSDP/blob/HEAD/docs/migration_guide.md)). Релизных тегов нет, зависимость `torch` не ограничена по версии, тестов и примеров использования `fully_shard` в репозитории нет; Dockerfile и примеры не обновляются с 2024-05-27. Поэтому правила Y-LIB-014 … Y-LIB-016 опираются на код и имеют среднюю уверенность.

**Yandex AI Studio SDK.** Репозиторий и пакет переименованы 2026-01-27; старый адрес перенаправляет на новый. Документация сервиса описывает порядок выбора учётных данных и 12-часовой срок жизни IAM-токена; повторы, тайм-ауты и логирование описаны только в коде ([документация](https://aistudio.yandex.ru/ru/docs/ai-studio/sdk/), [`_retry.py`](https://github.com/yandex-cloud/yandex-ai-studio-sdk/blob/master/src/yandex_ai_studio_sdk/_retry.py)). Правила Y-LIB-017 … Y-LIB-022. Проверкой исходников уточнено имя асинхронного класса верхнего уровня - `AsyncAIStudio`.

**Внешние библиотеки.** Основной фреймворк глубокого обучения по всем найденным свидетельствам - PyTorch (все 12 репозиториев выборки; распределённые обучения в YTsaurus идут на PyTorch; YaFSDP - надстройка над PyTorch), формат публикации моделей - Hugging Face с примерами на `transformers`, vLLM и PEFT; JAX и TensorFlow в выборке не используются (0 из 12). Правил Яндекса для этих библиотек нет - публичных данных не найдено; профиль приводит рекомендации самих проектов (Y-LIB-023 … Y-LIB-029) с пометкой «не Яндекс»: PyTorch (сериализация, случайность, `cudnn.benchmark`), scikit-learn (`random_state`, запрет `fit` на тестовых данных), Hugging Face (карточки, safetensors). Как в Яндексе используют внешние библиотеки внутри, публично известно только из статьи о YTsaurus (PyTorch, распределённое обучение) и из кода `yandex-research`.

### F.3. MLOps

**Версионирование данных и моделей; что нельзя коммитить.** Письменного правила нет, но практика единообразна: во всех 12 репозиториях `yandex-research` данные и веса лежат вне git, а конфиги запусков и отчёты - в git ([Y-MLOPS-001](../docs/ml/mlops.md)). Порог размера файла задан в одном репозитории - в SDK, хуком `check-added-large-files` с порогом 10 000 КБ (Y-MLOPS-002). О DVC и Git LFS в практике Яндекса публичных данных не найдено; оба инструмента включены как альтернативы «не Яндекс» (Y-MLOPS-003, Y-MLOPS-004); лимиты GitHub на размер файла (50 и 100 МиБ) - из GitHub Docs. Про секреты есть прямой совет документации DataSphere - не выводить секрет в ячейке (Y-MLOPS-005, MUST в профиле); сканеры секретов (gitleaks, detect-secrets) - «не Яндекс».

**Пайплайны обучения и инференса - принципы, а не инструкции к платформам.** Публично описаны три платформы и три разных эпохи: Нирвана - статья 2018 года о закрытой платформе; YTsaurus - статья декабря 2025 года; DataSphere - актуальная документация облака для внешних клиентов ([Нирвана](https://habr.com/ru/companies/yandex/articles/351016), [YTsaurus](https://habr.com/ru/companies/yandex/articles/979336/), [DataSphere Jobs](https://yandex.cloud/ru/docs/datasphere/concepts/jobs/)). Общие черты - граф шагов с явными входами и выходами, декларативное описание шага, переиспользование результатов детерминированных шагов (кэш блоков в Нирване), вариация эксперимента как копия с другими параметрами ([fork задания](https://yandex.cloud/ru/docs/datasphere/concepts/jobs/fork)), оркестрация извне ([Airflow](https://yandex.cloud/ru/docs/datasphere/concepts/jobs/airflow)). Профиль излагает их как принципы с пометкой «интерпретация» и оформляет только два проверяемых правила (Y-MLOPS-006, Y-MLOPS-007). О Нирване после 2018 года, о версионировании её операций и о её связи с YTsaurus публичных данных не найдено; есть лишь следы в коде - библиотека `nirvana_dl` и модуль `nirvana_utils.py` в исследовательском репозитории 2026 года и переменные «Nirvana operations» в исходниках документации CatBoost. Состояние DataSphere тоже менялось: анонс 2020 года обещал автоматические чекпойнты и версии «данные, код, состояние», документация 2026 года просит сохранять состояние самому, а serverless-режим снят 2024-03-01 ([release notes](https://yandex.cloud/en/docs/datasphere/release-notes)).

**CI/CD для ML, тесты данных и моделей.** Единственное письменное описание - туториал Yandex Cloud: GitLab CI обучает и тестирует модель на merge request, запуск пишется в GitLab Model Experiments через MLflow API и продвигается в версию модели ([туториал](https://yandex.cloud/ru/docs/architecture/mlops-in-managed-gitlab), 2026-10-01). В практике картина двойная: тесты на pull request запускаются в 19 из 25 репозиториев Яндекса общего измерения, но в исследовательских репозиториях CI нет (0 из 12), тесты есть в одном. Тесты данных и моделей и критерии готовности к продакшену - публичных данных не найдено; правила Y-MLOPS-010 … Y-MLOPS-012 взяты из документов Google и статьи «The ML Test Score» с пометкой «не Яндекс».

**Реестр моделей, мониторинг, дрейф, откат.** О внутреннем реестре моделей, мониторинге качества, детекции дрейфа и процедурах отката публичных данных не найдено. Есть облачные механизмы: GitLab Model Registry в туториале, ресурс «модель» DataSphere без описанного версионирования, алиасы и ноды для выкладки, проверки состояния и сервисные метрики нод ([Inference](https://yandex.cloud/ru/docs/datasphere/concepts/deploy/), [мониторинг](https://yandex.cloud/ru/docs/datasphere/concepts/deploy/monitoring)). Страница мониторинга DataSphere говорит только о запросах, кодах ответов и времени ответа. Ближайшее к откату описание - аварийное отключение эксперимента в лекции об A/B-тестировании 2017 года ([Хабр](https://habr.com/ru/companies/yandex/articles/342704)). Правила Y-MLOPS-013 … Y-MLOPS-017 - с альтернативами «не Яндекс» (MLflow Model Registry).

**Документация моделей и данных.** Стандарта нет, но практика есть: три карточки моделей 2025-2026 годов на Hugging Face построены одинаково - описание, бенчмарки с условиями замера, использование, дообучение - и не содержат разделов об ограничениях, смещениях и цитировании; у AliceAI-T5-35B-A0.6B поле лицензии в метаданных не заполнено, у AliceAI-Foundation раздел о данных сводится к двум фразам ([huggingface.co/yandex](https://huggingface.co/yandex)). Для данных найден один пример - [datasheet TabReD](https://github.com/yandex-research/tabred/blob/HEAD/datasheet.md) в формате «Datasheets for Datasets». Правила Y-MLOPS-018 … Y-MLOPS-021; шаблоны `MODEL_CARD.md` и `DATA_CARD.md` повторяют порядок разделов карточек Яндекса и добавляют недостающие разделы с пометкой «не Яндекс».

### F.4. C++ в ML

Отдельного публичного гайда по C++-коду инференса и расширений нет. На код CatBoost действует общий стайлгайд C++ в редакции CatBoost (стиль Аркадии, обязателен для контрибьюторов) плюс требование компилируемости CUDA-кода под C++17 или C++20; к раскладке относятся подкаталоги `ut` рядом с каждой библиотекой, разделение библиотек обучения и применения и совет брать для размеров и индексов беззнаковые 64-битные типы (дополнения команды, 2023-12-01). По коду видны приёмы, а не правила: C API с непрозрачными хэндлами, результатом `bool` и потоко-локальной строкой ошибки ([c_api.h](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/catboost/libs/model_interface/c_api.h#L76-L92)); автономный вычислитель на `std::`-типах без util ([evaluator.h](https://github.com/catboost/catboost/blob/963da016857b91dc729f6f8c61a5711e608ea1d8/catboost/libs/standalone_evaluator/evaluator.h#L8-L53)); компиляция экспортированного C++-кода модели в тестах; потокобезопасная библиотека применения рекомендована, standalone evaluator прямо не рекомендован. О правилах для C++-расширений Python и GPU-кода публичных данных не найдено. Правила [Y-MLOPS-022, Y-MLOPS-023](../docs/ml/mlops.md), Y-LIB-010 и Y-ML-016 … Y-ML-018 (Y-MLOPS-022 - MUST по формулировке CatBoost, Y-ML-018 - SHOULD по формулировке конкретного пункта дополнений).

**Что уточнено сверх заметок исследования.** Тексты документации Yandex Cloud распространяются под CC BY 4.0: это следует из файла LICENSE репозитория [yandex-cloud/docs](https://github.com/yandex-cloud/docs), в котором лежат страницы DataSphere и оба туториала; лицензия сайта документации AI Studio SDK осталась непроверенной. Страницы DataSphere о мониторинге нод, повторном запуске заданий и Airflow в заметках исследования отсутствовали и открыты при подготовке профиля; вывод «о качестве модели и дрейфе публичных данных не найдено» при этом сохраняется.
